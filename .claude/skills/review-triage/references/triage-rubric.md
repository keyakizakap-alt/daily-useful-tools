# 指摘の分類ルーブリック

各指摘に対し、上から順に判定する。最初に該当した分類を採用する。

## E: 誤検知 (False positive)

次のいずれかに当てはまる場合、E。

- レビュワーが参照していないファイル・設定・仕様に、既に対処が存在する
- 指摘の前提が実際のコードや実行環境と異なる（読み違え、古い版を見ている）
- 「意図的にそうしている」設計であり、その意図が Issue またはコメントに記録されている
- 静的解析・bot の既知の偽陽性パターン

**判定に必要な作業**: 該当箇所を実際に読んで確認する。読まずに E と決めない。
**出力**: 却下理由 + 根拠となるファイル/行番号。

## D: 観点間矛盾 (Conflicting)

- この指摘に従うと、別観点のレビュワーが不合格にすると分かっている条件を踏む
- 過去のラウンドで、この修正の逆方向の指摘を受けたことがある（台帳で確認）
- 指摘同士がトレードオフ（性能 vs 可読性、抽象化 vs 単純さ、厳格さ vs 後方互換 など）の両端にある

**出力**: Gate 2 のコンフリクト表へ送る。単独で修正着手しない。

## B: 正当だがスコープ外 (Out-of-scope)

- 指摘は技術的に正しいが、Gate 0 の受け入れ条件のどれにも紐づかない
- 今回の差分が原因ではない既存の問題（差分の前から存在する）
- 「ついでにこれも直すべき」型の提案

**注意**: 差分が原因で顕在化した既存問題は B ではなく A/C。「自分の変更が引き金か」を必ず確認する。
**出力**: 別Issue化の提案 + 今回直さない理由。

## C: 対症療法 (Symptomatic)

指摘された**問題**は実在するが、提案された**修正方法**が次のいずれかである場合。

- 例外を握り潰す / 条件分岐を足して個別ケースだけ回避する
- 呼び出し側だけ直し、原因のある呼ばれる側を放置する
- テストを通すためのハードコード、閾値の緩和、アサーションの削除
- 同じ問題が他の箇所にもあるのに、指摘された1箇所だけ直す
- 型・null・境界値の問題を、キャストや非nullアサーションで黙らせる

**出力**: 問題は受理。修正方法は Gate 3 で設計し直す。レビュワーには「問題は同意・方法は変更」を返す。

## A: 根本 (Root)

上のいずれにも当たらず、受け入れ条件に直結し、提案された修正が原因そのものに届いている。

**出力**: そのまま Gate 3 → Gate 4 へ。

---

## 分類の健全性チェック

分類し終えたら確認する。

- 全件が A になっていないか（→ 分類が甘い。C と E を疑う）
- 全件が E になっていないか（→ 防衛的になりすぎ。指摘を読み直す）
- 同一の根本原因に紐づく A/C が複数ないか（→ 1つの統合パッチにまとめる）
- 2ラウンド目以降で、前回 A として直した箇所に再指摘が来ていないか（→ 前回の修正が C だった証拠。根本に遡る）
