# 観点間コンフリクトの解消手順

複数の観点別レビュワーを並列で走らせると、**互いの合格条件が両立しない指摘**が必ず発生する。
これを着手前に解かずに片方ずつ対応すると、修正と再指摘が交互に往復し続ける（ピンポン・ループ）。

## 手順

### 1. コンフリクト表を作る

| # | 観点X の要求 | 観点Y の要求 | 衝突点 | 背後の本当の要求(X) | 背後の本当の要求(Y) | 採る解 |
|---|---|---|---|---|---|---|

「背後の本当の要求」を書くのが要点。指摘の**表現**は衝突していても、**目的**は衝突していないことが多い。

- 例: 「エラーを握り潰すな」(堅牢性) vs 「ユーザーに例外を見せるな」(UX)
  → 背後: 障害を検知可能にしたい / 利用者の操作を止めたくない
  → 第三の解: 内部ではログ・監視に記録し、UI には回復可能なメッセージを出す。両方満たす。

### 2. 解の優先順位

1. **統合解** — 両方の背後の要求を満たす第三の設計。まずこれを探す。
2. **層の分離** — 片方を別のレイヤ・別の関数・別の設定値に移し、両立させる。
3. **ゴール優先での選択** — 統合解が無い場合のみ。Gate 0 の受け入れ条件により近い方を採る。
4. **人間にエスカレーション** — トレードオフが仕様判断（性能目標、互換性方針、セキュリティ許容度）に依存する場合は、勝手に決めない。

### 3. 採らなかった側への返信

必ず返す。「観点Y の指摘は〜という理由で、観点X の要求と両立しないため、〜という設計を採用した」。
返信せずに無視すると、次ラウンドで同じ指摘が再生成される。

## よく出るコンフリクトの型

| 型 | 典型的な衝突 | 統合解の方向 |
|---|---|---|
| 堅牢性 vs UX | 例外を投げる / 握って表示 | 記録は厳格に、表示は穏当に |
| 抽象化 vs 単純さ | 共通化しろ / 過剰設計だ | 3回目の重複まで共通化しない（Rule of three） |
| 性能 vs 可読性 | 最適化しろ / 読めない | 計測で必要性を示せた箇所のみ最適化し、理由をコメントに残す |
| 厳格な型 vs 後方互換 | 型を絞れ / 既存呼び出しが壊れる | 新APIを追加し、旧APIは非推奨として残す |
| 網羅テスト vs 差分最小 | ケースを足せ / スコープ外だ | 受け入れ条件に紐づくケースのみ今回、残りは別Issue |
| セキュリティ vs 利便性 | 検証を足せ / 手順が増える | 安全側をデフォルトにし、緩和は明示的なオプトインにする |

## 禁止手

- 両方の指摘を同時に満たそうとして、両方に対する中途半端な対処を入れる
- 片方の観点のレビュワーだけ再実行して合格を取り、もう一方を無視する
- コンフリクトの存在自体を報告せずに、片方を黙って落とす
