# ループ検知とエスカレーション基準

## ラウンドの定義

1ラウンド = 「修正を投げる → レビュワー群から指摘が返る」の1往復。

## 停止シグナル

以下のいずれかを観測したら、**実装を止めて人間に判断を仰ぐ**。

1. **3ストライク**: 同一ファイル・同一関数・同一テーマで3ラウンド連続で指摘が発生
2. **往復**: 前ラウンドで自分が入れた修正に対する指摘（＝修正が新たな指摘を生んだ）が2回続く
3. **反転**: 過去に「Xにしろ」と言われて直した箇所に「Xをやめろ」と言われた
4. **膨張**: 差分の行数がラウンドごとに増え続け、受け入れ条件の充足率が上がっていない
5. **目的のすり替わり**: 直近のラウンドで書いた変更が、Gate 0 の受け入れ条件のどれにも紐づいていない
6. **未着手**: 3ラウンド経過しても受け入れ条件のチェックが1つも増えていない

## 停止時の報告フォーマット

```
## レビューループを検知したため停止しました

- 検知シグナル: （上の1〜6のどれか）
- 経過ラウンド数:
- 本来のゴール（Gate 0 の再掲）:
- 受け入れ条件の充足状況: 3件中1件
- 周回している指摘のテーマ:
- 各ラウンドで何が起きたか: （台帳の要約）

### 分析
- ループの原因（推定）:
- レビュワーの指摘が表層的だと判断した根拠:
- 観点間で矛盾している要求:

### 提案
- 案1（推奨）: 設計レベルでの変更 — 内容 / 影響範囲 / 解消される指摘
- 案2: 今回のスコープを縮小し、残りを別Issue化 — 分割案
- 案3: レビュー観点そのものの見直し — どの観点のどの条件が過剰か

### 判断が必要な点
- （人間に決めてほしいトレードオフ）
```

## やってはいけないこと

- 「あと1周だけ」でラウンドを継続する
- レビュワーを再実行して合格を引くまで回す
- 指摘の出た箇所だけを消す・無効化する・テストを緩める
- 停止せずに、レビュワーの合格だけを取って Issue 未解決のまま完了報告する
