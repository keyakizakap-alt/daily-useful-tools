# review-triage — レビュー沼を抜けるためのトリアージ・ゲート

## このスキルが解く問題

観点別に並列で走らせたレビュワーの指摘に素直に従うと、次の失敗モードに入る。

- レビュワーの提案は**症状に対する表面的な処方**であることが多く、根本原因が残るため別の形で再発する
- 観点Aを満たす修正が観点Bの不合格条件を踏み、**指摘が無限に生成される**
- メインエージェントの目的関数が「Issue の解決」から「**全レビュワーの合格**」にすり替わる
- 結果、差分だけが膨らみ、Issue は解決しないまま周回する

**このスキルは修正コードを書く前に必ず通す関所である。** 指摘を受け取ってから編集を始めるまでの間に、下記のゲートを順に通す。

## 大原則（迷ったらここに戻る）

1. **Done の定義は「Issue の解決＋リグレッションなし」であり、「レビュワー全員の合格」ではない。**
2. **レビュワーの指摘は「バグ報告」として尊重し、「修正方法の提案」は仮説として扱う。** 何が壊れているかは信じる。どう直すかは自分で決める。
3. **指摘の却下は正当な結論である。** 根拠を書いて返すことは、サボりではなく仕事である。
4. **同じテーマの指摘が2回目に出たら、それは修正が浅かったサインである。** 3回目はループ確定として停止する。
5. **修正は「指摘ごと」ではなく「根本原因ごと」に1つの統合パッチとして設計する。**

## 手順

### Gate 0 — ゴールの再宣言（必須・省略不可）

コードに触れる前に、以下を明文化する。既に書いてある場合も、ラウンドごとに読み直す。

```
## 本来のゴール
- Issue/依頼が解決しようとしている問題:
- 受け入れ条件（満たせば完了と言えること）:
  - [ ]
  - [ ]
- 非ゴール（今回やらないと決めたこと）:
```

受け入れ条件に含まれない指摘は、原則としてスコープ外候補である（後述の分類 B）。

### Gate 1 — 指摘の棚卸しと分類

すべての指摘を1つの表に集約する。観点別レビュワーが別々に返してきた指摘も、**必ず1枚にまとめてから**判断する。分類の詳細な判定基準は `references/triage-rubric.md` を読む。

| # | 出所(観点) | 指摘の要旨 | 提案された修正 | **本当の問題は何か** | 分類 | 対応 |
|---|---|---|---|---|---|---|

分類は5つ:

- **A: 根本 (Root)** — 受け入れ条件に直結し、原因まで特定できている → 直す
- **B: 正当だがスコープ外 (Out-of-scope)** — 指摘自体は正しいが Issue の外 → 別Issue化して返信、今回は直さない
- **C: 対症療法 (Symptomatic)** — 指摘は妥当だが提案された修正が表層的 → **問題は受け入れ、修正方法は自分で設計し直す**
- **D: 観点間矛盾 (Conflicting)** — 他観点の指摘と両立しない → Gate 2 へ送る
- **E: 誤検知 (False positive)** — 前提誤り・仕様誤読・既存の意図的な設計 → 根拠を添えて却下

**C と E を作らずに全部 A として処理し始めた瞬間に沼が始まる。** 分類表に C と E が1つも無い場合は、分類が甘くないか一度疑う。

### Gate 2 — 観点間コンフリクトの解消（着手前に）

分類 D、および「Aの修正が他観点の合格条件を踏みそうな箇所」を洗い出し、着手前に解く。手順は `references/conflict-matrix.md` を読む。

原則: **どちらかを選ぶのではなく、両方の背後にある要求を満たす第三の設計を探す。** それが無い場合のみ、Issue のゴールに近い方を採り、もう一方には却下理由を返す。

### Gate 3 — 根本原因の特定

分類 A と C について、指摘そのものではなく原因を書く。

```
症状（レビュワーが見たもの）:
なぜそうなるか（1段目）:
なぜそうなるか（2段目）:
根本原因:
この根本原因を直すと、同時に解消される指摘: #, #, #
```

**複数の指摘が1つの根本原因に収束したら、それが本命の修正である。** 指摘の数だけパッチを当ててはいけない。

### Gate 4 — 統合修正方針の確定

```
## 修正方針
- 変更するもの（根本原因への対処）:
- 意図的に変更しないもの（分類 B / E）とその理由:
- この方針で満たされる受け入れ条件:
- この方針が踏みうる他観点の懸念と、その先回りの手当て:
- 検証方法（この修正が効いたと言える確認手段）:
```

ここまで書き終えて、はじめてコードを編集する。

### Gate 5 — ループ検知

ラウンドごとに `templates/review-ledger.md` の台帳を更新する。判定基準は `references/loop-detection.md` を読む。

- **同一テーマ・同一箇所で3ラウンド目に入ったら、実装を停止する。**
- 停止時にやること: 台帳を提示し、(a) 設計レベルの変更提案、(b) レビュー観点自体の見直し提案、(c) 判断が必要な点、をまとめて**人間に判断を仰ぐ**。
- 「もう一度レビュワーに投げて様子を見る」は禁止手である。それがループの燃料になる。

## レビュワーへの返し方

分類 B / C / D / E は、黙って無視せず必ず返信する。テンプレートは `templates/response-template.md`。

- **B**: 「指摘は妥当。ただし本Issueの受け入れ条件外のため別Issueとする」
- **C**: 「問題の存在は同意。ただし提案の修正は症状への対処のため、根本原因である〜を修正した」
- **D**: 「観点Xの指摘と両立しないため、〜という設計で両方の要求を満たした」
- **E**: 「〜という前提のため、現状の実装が意図した挙動である」

## アンチパターン（これをやったら沼）

- 指摘を1件ずつ順番に潰す（統合設計をしない）
- レビュワーの提案コードをそのまま貼る
- 「レビュワーが通らないから」を理由に設計を歪める
- 指摘が増えるたびに差分を広げる（スコープクリープ）
- 却下の判断を避けて、全指摘を機械的に受け入れる
- ループに気づいても、あと1周だけ、と続ける
