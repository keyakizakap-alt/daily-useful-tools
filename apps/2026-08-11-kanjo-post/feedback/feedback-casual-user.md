# フィードバック: 一人暮らしの社会人ユーザー視点

レビュー対象: `apps/2026-08-11-kanjo-post/src/`(実装)、`design/`、`requirements/`
レビュー方法: ドキュメントとコード(`index.html`, `js/*.js`, `css/*.css`)を読み、実際に「上司に理不尽なことを言われた夜、モヤモヤを書いて封をし、後日読み返す」という主要ユースケースを一人のユーザーとして操作する想定でレビューしました。

---

## 総評

コンセプト(時間差で自分に手紙を届ける)がUIの隅々まで一貫していて、実際に夜疲れて使う場面を想像すると好印象です。「送らない宣言」の常時表示や、非断定トーンのコピー、封をするアニメーションなど、design.mdで掲げた思想がちゃんとコードに落ちている点は素直に評価できます。一方で、**一晩のモヤモヤを安心して預けられるか**という観点では、いくつか気になる挙動(特にカスタム配達日と、データ消失時の逃げ道のなさ)があり、そこは早めに直したほうが良いと感じました。

---

## 良い点

1. **「送らない宣言」が常時見える安心感**
   ホーム画面上部・速達フォームの説明文に「誰にも送られません」が繰り返し出てくるので、書いている最中も「これ誰かに見られるかも」という不安が湧きにくいです(`index.html` `no-send-badge`、`compose` Step1の`field-hint`)。

2. **宛先が属性選択式で実名を書かせない設計**
   `letters.js` の `RELATIONS` が固定タグのみで、フォームにも自由入力欄がないため、勢いで実名を書いてしまう事故が構造的に起きません。疲れているときほど「うっかり書いてしまう」リスクがあるので、この制御はありがたいです。

3. **未配達の手紙が中身を一切見せない**
   `buildEnvelopeCard` で `status === "sealed"` の間はタグも本文も出さず「まだ届いていません」だけを表示し、タップしても「まだ届いていません。届く日までそっとしておきましょう」とトーストが出るだけ(`main.js` `buildEnvelopeCard`)。ここで内容を覗き見できてしまうと「封をする」体験が台無しになるので、しっかり守られているのは良いです。

4. **非断定・非評価のコピーが徹底されている**
   「未読」ではなく「まだ届いていません」、ダッシュボードも「気づき」であって「評価やランキングではなく」と明記(`index.html` dashboard画面)。人を晒すようなランキング表現(「一番あなたを怒らせた人」的なもの)が入っていない点も設計方針どおりです。

5. **片手操作への配慮**
   主要ボタンが画面下部に固定(`bottom-actions`)、ボタンの `min-height: 52px`、チップも `min-height: 52px` と、深夜の疲れた状態でも押しやすいサイズになっています。ステップフォームも1画面1テーマで迷いにくいです。

6. **振り返り(往復書簡)の見せ方**
   開封後に「今どう思うか/実際どうなったか/次にどうしたいか」を何度でも追記でき、時系列で並ぶ(`buildReflectionItem`)。1回書いて終わりの日記アプリと違い、「その後どうなったか」を後から積み重ねられるのは、このアプリならではの価値だと感じました。

## 改善すべき点・バグ

### 1. カスタム配達日で「今日」や過去日を選ぶと、時間差なしで即配達されてしまう(重大)
`letters.js` の `computeDeliverAt`:
```js
var custom = new Date(customDateStr + "T00:00:00");
```
カスタム日付は「その日の午前0時」として扱われます。しかも `<input type="date">`(`index.html` `customDateInput`)に `min` 属性が設定されていないため、**今日の日付や過去の日付も選択できてしまい**、次にアプリを開いた瞬間(あるいは同じ日にもう一度郵便箱を見た瞬間)に配達済みになります。
- このアプリの核である「時間差を置いて反芻を止める」という体験が、カスタム日付を選んだユーザーにとってはほぼゼロになってしまいます。
- バリデーションは「日付が選ばれているか」しかチェックしておらず(`validateComposeInput`)、「今日以前を選んだら警告する」といったガードがありません。
- 改善案: `customDateInput` に `min` を明日以降に設定する、または `computeDeliverAt` で「now以前の日付が指定されたら翌日として扱う/エラーにする」処理を追加してほしいです。

### 2. データが端末のブラウザにしかなく、消失時の警告や誘導が弱い
要件どおりlocalStorageのみで完結する設計は理解していますが、実際に使うユーザーの立場だと、
- 初回起動時や、手紙が数通たまった時点で「バックアップを取っておくと安心です」という案内が**設定画面の奥にしかない**(ホーム画面には出てこない)。
- iPhoneのSafariでプライベートブラウズを使っていたり、ストレージ容量不足でブラウザがキャッシュを掃除したりすると、何の前触れもなく全ての手紙が消えます。
- 数週間〜1か月後に届くことを前提にした手紙なので、「うっかり忘れて機種変更してしまった」「ブラウザデータを消してしまった」は日常的に起こり得るシナリオです。ホーム画面や、手紙が一定件数(例: 5通)たまったタイミングで軽くバックアップを促すトーストなどがあると安心感が上がると思います。

### 3. 「封をする」前にレビュー画面がなく、誤字脱字を直す手段が封印後は一切ない
Step3で「封をする」を押すと即座に `createLetter` が実行され、保存後は編集・削除するAPIがコード上どこにも存在しません(`letters.js` に `updateLetter` や削除系のUI導線なし。`removeLetter` 関数はあるが呼び出し元がゼロ)。
- 誤字や「関係性タグを間違えて選んだ」場合、配達されるまで(最短でも3日後)一切訂正できません。感情的になっている状態で書いているからこそ、送信前の最終確認(サマリー表示)があると安心して封をできると思います。
- また、書き間違えて「もうこの手紙自体をなかったことにしたい」と思っても削除する手段が画面上に存在しません(`removeLetter` は実装されているのに未接続)。心理的ケアを謳うアプリなのに「やっぱりやめる」ができないのは気になりました。

### 4. 速達フォームを離脱すると入力内容が無警告で消える
Step1〜3のどこかで戻る(ヘッダーの←ボタンやブラウザバックでホームへ)、あるいはタブを閉じると、`resetCompose` が呼ばれる/ページが破棄されるだけで、`beforeunload` 等の確認は一切ありません(`main.js` `wireStaticEvents` の back 処理)。
- 夜、勢いで書き始めたものの電話がかかってきた・眠くなった等で離脱すると、それまで書いた内容が跡形もなく消えます。「一言だけでも下書きとして残しておいてほしかった」という体験になりやすいです。下書きの自動一時保存(localStorageに `draft` として都度保存)があると親切だと思います。

### 5. チップ選択のアクセシビリティ表現が視覚のみ
`buildChips` で生成されるチップは選択状態を `.is-selected` クラス(背景色の変化)のみで表現しており、`aria-pressed` や `aria-selected` がありません。スクリーンリーダー利用者には「選択済みかどうか」が伝わりません。心理的安全性を重視するアプリだからこそ、視覚に頼れない利用者への配慮も欲しいところです。

### 6. インポートの「マージ」挙動がやや不親切
設定画面の説明は「同じ手紙(同一ID)は上書きされ、それ以外は追加されます」とありますが、実際に何件が新規追加され何件が上書きされたのか、インポート後に内訳が分かりません(`showToast("読み込みました。")` のみ)。機種変更時などに「本当に全部戻ってきたか」を確認しづらく、少し不安が残ります。

### 7. 配達通知音が最初の起動時には鳴らない可能性がある
`runDeliveryCheck` は `DOMContentLoaded` → `init()` → `navigate("home")` の流れでユーザー操作なしに呼ばれます。多くのモバイルブラウザは「ユーザー操作(タップ)なしに音を鳴らすこと」を禁止しているため、アプリを開いた瞬間にすでに配達条件を満たしている手紙があっても、初回はチャイムが鳴らない可能性が高いです(`sound.js` は例外を握りつぶして静かに諦める実装なので、鳴らなくてもエラーにはならず気づきにくいのも問題です)。配達バナー自体は表示されるので致命的ではないですが、「優しい音で知らせる」という体験が実際には機能しない場面が多そうです。

### 8. 傾向ダッシュボードの「期間ごとの手紙の数」が createdAt 基準
`aggregateByPeriod` は手紙を書いた日(`createdAt`)を基準に集計しています。「気まずくなりやすい場面のパターンに気づく」という目的には合っていますが、週/月トグルを切り替えても直近数件しか手紙がない間はほぼ差が出ず、グラフの意味を実感しづらいです(バグではなく、初期利用時の体験として気になった点)。

## 使いにくいと感じた細かい点

- 手紙一覧のフィルタ行(ステータス・関係性)が横スクロールチップになっていますが、選択中のフィルタがスクロールで隠れて見えなくなることがあり、「今どのフィルタがかかっているか」を確認するために毎回スクロールを戻す必要がありました。
- 詳細画面の追記フォームで、3つの欄すべてを空にして送信するとエラーになりますが(`addReflection`)、エラーメッセージ表示位置がボタンの上のみで、フォーム自体の枠の色が変わらないため、初見だと「なぜ送信できないか」に一瞬気づきにくいです。
- ホーム画面の「配達待ち」「届いた手紙」タイルが件数だけのシンプルな表示で、次にいつ何が届くか(直近の配達予定日)がホームから分からず、毎回一覧を開いて確認する必要があります。

---

## まとめ

コンセプトとUIトーンの一貫性は非常に良く出来ており、「静かに気持ちを預けられる場所」という狙いは体感できました。ただし実際の生活の中で使うことを考えると、
1. カスタム配達日の過去日/当日選択を防ぐ、
2. データ消失への備え(バックアップ誘導)を強める、
3. 封をする前の最終確認・封後の取り消し手段、
4. フォーム離脱時の下書き保存、

の4点は、「安心して本音を預けられるかどうか」に直結するため優先度高めで直していただきたいです。
