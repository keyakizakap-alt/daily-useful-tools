## 4. 根本原因への収束（手順4）

14件の指摘は **4つの根本原因** に収束した。指摘の数だけパッチを当てない。

### 根本原因1 — 候補の提示に「時期の多様性」がない（#1, #2, D-1）

```
症状:   おすすめプラン12件のうち、実質4時期しか含まれていない。
        「ほかに973件」という表示が、選べない感覚を強めている。
根本原因: 順位付けが効率の一次元のみで、「同じ連休の変種」と
        「別の時期の候補」が同じ土俵で競合している。
同時に解消: #1, #2, D-1
方法:   planner に純関数を2つ追加する。
        - dropDominatedPlans()  … 上位候補に完全に含まれ、かつ有給も多く使う劣った候補を落とす
        - selectVariedPlans()   … 範囲が重なる候補は最大 maxPerCluster 件までにして limit 件選ぶ
        表示ロジックを app.js から planner.js へ移し、単体テストの対象にする。
検証:   planner のテストで「同一クラスタが2件以下」「上限件数」「順序の決定性」を検査。
        ブラウザ確認で表示される時期の数を数える。
```

### 根本原因2 — テーマ状態の単一情報源が localStorage になっている（#3, #4）

```
症状:   (a) 「保存した条件を消す」後も yasumitsunagi.theme.v1 が残る
        (b) localStorage が使えない環境でテーマ切替が「ライト」で固着する
根本原因: 現在のテーマを state に持たず、クリックごとに loadTheme() で
        localStorage から読み直していた。保存が失敗する環境では常に
        既定値 'auto' が返るため、次の状態が計算できない。
        消去処理も「removeItem → applyTheme() が再保存」で自分の消去を打ち消していた。
同時に解消: #3, #4
方法:   state.theme を単一の情報源にする。applyTheme(theme, {persist}) は
        state と DOM を更新し、保存は副作用として分離する。消去時は persist: false。
検証:   ブラウザ確認に2項目追加。
        「消去後に localStorage の当アプリのキーが0件」
        「localStorage が例外を投げる環境でも 自動→ライト→ダーク→自動 と巡回する」
```

### 根本原因3 — 安全性が人間の注意力に依存している（#5, #6, #7, #8）

```
症状:   CSP の不要な緩和、meta では無視される指令、make() の無制限な属性設定を
        いずれも「レビューで」発見した。
根本原因: 守るべき不変条件がコードと静的解析に書かれておらず、
        レビュワーが気づくかどうかに委ねられていた。
同時に解消: #5, #6, #7, #8
方法:   (1) CSP から 'unsafe-inline'（style-src）を削除し、frame-ancestors は配信ヘッダへ
        (2) make() が on* / href / src / srcdoc / formaction 属性を受け取ったら例外を投げる
        (3) 静的解析に「style-src に unsafe-inline を書かない」「frame-ancestors を meta に書かない」を追加
検証:   npm run check、ブラウザ確認（CSP 違反が0件で描画されること）
```

### 根本原因4 — 祝日計算の前提が暗黙（#9）

```
症状:   年境界をまたぐ振替休日・国民の休日を扱えない。
根本原因: 「現行法では年境界をまたぐ休日は発生しない」という前提に依存しているが、
        その前提がコードにもテストにも書かれていない。
方法（提案とは変える）: 前後年を参照する実装にはしない（複雑さに対して得るものがない）。
        代わりに前提をコメントで明文化し、前提が崩れたら落ちるテストを置く
        （12/30・12/31 に祝日がなく、1/1 の前日が祝日でないこと）。
同時に解消: #9
検証:   2007〜2099年の全域で前提が成立することをテストで確認
```
