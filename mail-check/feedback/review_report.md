## 4. 根本原因と統合方針（トリアージ手順4）

```
症状（レビュワーが見たもの）:
  R1 長い行があると他の指摘が消える / R2 引用行の添付を拾う / R3 無視が復活する
  R5 低だけで0点 / R12 選択中の指摘がずれる

根本原因:
  原因1【指摘の重なり解消】広い範囲の助言的指摘が、具体的な指摘に優先してしまう（R1）
  原因2【引用除去】位置を保存しない除去のため、文書チェックが原文基準に戻らざるを得ない（R2）
  原因3【指摘の同一性】絶対位置を同一性に含めている（R3・R12 が同じ根を持つ）
  原因4【環境依存の構文】後読み正規表現の評価がファイル全体の読み込みを止める（R4）
  原因5【評価指標】1つの数字に「送信可否」と「仕上がり」を載せている（R5）

この原因を直すと同時に解消される指摘:
  原因1 → R1 と、将来の「広い範囲のルール」全般
  原因2 → R2 と、今後の文書チェック追加時の同種バグ
  原因3 → R3, R12
  原因5 → R5, D2（コンフリクト）

意図的に変更しないもの:
  R9（件名の全ルール適用）・R14（絵文字の文字数）= B、別Issue として docs に記録
  R10（すみませんの置換）・R11（例文のダミー資格情報）= E、根拠を本記録に残す

先回りで手当てする他観点の懸念:
  ・「狭い指摘を優先」に変えることで、重要度の高い指摘が隠れないか
    → 重要度が第一キーであることは変えない。回帰テストで担保
  ・長行の指摘から位置を外すと、どの行かわからなくなる
    → 行番号をメッセージに入れる

検証方法:
  1. 回帰テストを追加（長行が他の指摘を隠さない／引用行の添付を拾わない／
     位置が動いても無視が続く／低の減点上限／ID 改名）
  2. `npm test`（全件グリーン）
  3. `npm run smoke`（file:// のブラウザで全経路）
  4. eslint + `npm audit`
```

## 6. 残っている限界（利用者に伝えるべきこと）

- ルールベースなので、**指摘は網羅的ではない**。文法的に正しくても意味が伝わらない文は検出できない。
- 件名に対しては専用の4チェック（空・長さ・用件・強い符号）のみで、敬語ルールは適用されない（R9）。
- 誤検出はゼロにできない。だから「無視」があり、重要度を色だけでなく文字でも示している。
- 絵文字を含む文字数表示は UTF-16 単位（R14）。判定結果には影響しない。
