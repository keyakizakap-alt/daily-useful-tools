# おくるまえに — 送信前にメールを点検する、通信ゼロの静的ツールを追加

## 1. アイデアの概要と解決する課題

日本語のビジネスメールには、送信直前に毎回立ち止まる小さな判断がいくつもある。

- 「了解しました」は社外に送っていいのか
- 「なるはやで」と書いたが、相手の「なるはや」は自分と同じか
- 「至急ご対応ください」は角が立たないか
- 宛名・結び・署名は揃っているか
- そして最悪の事故 —— **本文にパスワードを書いてしまっていないか**

既存の校正サービスや生成AIに本文を貼れば多くは解決するが、そこには別の問題がある。
**業務メールの本文は機密そのもの**で、外部に貼ること自体がリスクになる。

「おくるまえに」は、この点検を**ブラウザ内だけ・通信ゼロ**で行う。
本文を貼ると、敬語の誤り・二重敬語・尊敬謙譲の混同・期限のあいまいさ・言い方の圧・体裁の欠落・
機密情報の書き込みを重要度つきで指摘し、修正候補をその場で置換できる。

企画は10体の仮想エージェント（PM／ターゲットユーザー3体／アーキテクト2体／UI-UXデザイナー2体／
セキュリティエンジニア2体）による議論として実施し、候補5案から本案を採択した。議論の記録は
[`docs/requirements.md`](requirements.md) §1 にある。決定的だったのはセキュリティエンジニアの
「クラウドLLMに投げる設計なら反対する。ローカル完結であることを第一の製品価値にすべき」という指摘で、
これがそのまま技術選択を決めた。

## 2. 採択した技術アプローチとアーキテクチャ

| 方針 | 理由 |
|---|---|
| ルールベース（生成AIなし） | 本文を外に出さない。指摘理由を説明できる |
| 依存パッケージ 0 | サプライチェーン経路を作らない。`npm audit` の対象を構造的に持たない |
| 判定は DOM 非依存の純粋関数 | UI なしで単体テストできる。ルール追加が UI に波及しない |
| ビルド不要・`file://` で動く | 既存収録ツール（`index.html` / `weather/`）と同じ配布形態 |
| 外部フォント・CDN も使わない | 「通信ゼロ」の主張と実装を一致させる |

```
mail-check/          ← このツールだけで完結するディレクトリ（既存アプリと同じ配信面を共有しない）
├── index.html       画面（インラインスクリプトを持たない）
├── styles.css       ライト／ダークのトークン定義
├── engine.js        点検エンジン（純粋関数。UMD でブラウザと Node の双方から読む）
├── app.js           DOM 層（入出力・描画・保存）
├── package.json     開発用スクリプト（依存0件）
├── vercel.json / .vercelignore   このツール専用の Vercel プロジェクト設定
├── docs/            要件定義・設計・本記録
├── feedback/        レビューとトリアージの記録
└── tests/           単体テスト（node:test）・ブラウザ結合スモーク（playwright）
```

判定は2層構造。**スパンルール**（正規表現で本文中の位置を特定。50件）と
**文書チェック**（宛名・結び・署名・件名・文体など全体を見る関数。13件）に分け、
ルール追加はテーブルへの1行追加で済む。修正候補は文字列にも関数にもでき、
`ご確認して下さい → ご確認ください` のような語形に応じた置換ができる。

セキュリティ方針（詳細は [`architecture.md`](architecture.md) §4）:

- CSP で `default-src 'none'; script-src 'self'; connect-src 'none'; form-action 'none'; base-uri 'none'`
- 利用者入力が HTML になる経路を `buildSegments` → `escapeHtml` の一本に限定
- 下書きの端末内保存は既定 OFF。ON の間だけ保存し、解除時と（無効なままの）起動時に削除
- 正規表現はネストした量指定子を使わず、繰り返しの上限を明示
- ソースに鍵・トークンを持たない（そもそも通信しない）

## 3. Step 5〜6 で行った変更点とフィードバック対応

模擬ユーザー3体・デザイナー2体・アーキテクト2体・セキュリティエンジニア2体の観点でレビューし、
15件の指摘を得た。プロジェクト方針（`CLAUDE.md` / `.claude/skills/review-triage`）に従い、
**コードを編集する前に**全指摘を1枚の表に集約して分類した（A 根本4件 / B スコープ外2件 /
C 対症療法7件 / E 誤検知・意図的2件）。内訳と根拠は
[`review_report.md`](../feedback/review_report.md)。

### 指摘を根本原因に収束させた結果

| 根本原因 | 症状（レビュワーが見たもの） | 修正 |
|---|---|---|
| 重なり解消が「広い範囲」を優先していた | **長い行が1つあると、その行の敬語・表記の指摘がすべて消える**（R1） | 優先規則を「重要度 → 範囲が狭い順 → 開始位置」に変更。行全体を指す助言的な指摘は位置を持たせず行番号で示す |
| 引用除去が位置を保存していなかった | 引用行の「添付」で添付確認が出る（R2） | `stripQuotes` を同じ文字数の空白に置換する実装に変更し、文書チェックを引用除去後テキスト基準へ統一 |
| 指摘の同一性に絶対位置を含めていた | 「無視」が本文を1文字直すと復活する（R3）／選択中の指摘がずれる（R12） | `findingKey` から位置を除去。本文が変わったら選択状態を解除 |
| 環境依存の構文を前提にしていた | 後読み `(?<!…)` は未対応ブラウザで**ファイル全体が構文エラー**になり、ツールが白紙になる（R4） | 後読みを廃止し、前後の文字を見る `validate` 実装へ（挙動は同一）。後読みを使わないことをテストで固定 |
| 1つの数字に送信可否と仕上がりを載せていた | 重要度「低」だけで0点になり、送ってよいか読み取れない（R5） | 「低」の減点合計に上限（15点）。送信可否は要約文（高0件なら送って差し支えない）で伝える |

そのほか、装飾要素の `role="img"` 削除（R6）、ハイライトへの重要度補足（R7）、
「適宜・随時」を重要度「低」へ分離（R8）、保存無効時の起動時クリーンアップ（R13）、
ID と分類の不一致の解消（`double.goSasete` → `redundant.goSasete`、R15）。

### 却下・別Issue とした指摘（黙って落とさない）

- **却下（E）**: 「すみません」の置換候補を外す（R10 — `why` に代替案を併記済み、重要度は中、無視可能）／
  例文のダミーパスワードを消す（R11 — 機密検出の動作確認に必要で、例文であることは操作から明らか）
- **別Issue（B）**: 件名への全ルール適用（R9 — 位置空間の二重化が必要）／
  文字数カウントの書記素対応（R14 — 表示のみの問題）。`mail-check/docs/requirements.md` §8 に FUT-01〜04 として記録

### 検証

| 項目 | コマンド | 結果 |
|---|---|---|
| 単体テスト | `npm test` | **40 / 40 pass** |
| ブラウザ結合（`file://`、Chromium） | `npm run smoke` | **21 / 21 pass** |
| 構文チェック | `npm run lint` | エラーなし |
| 静的解析 | `eslint`（no-unused-vars / no-eval / no-new-func / eqeqeq ほか） | エラーなし |
| 依存監査 | `npm audit` | **0 vulnerabilities**（依存0件） |
| 通信の発生 | スモークで全リクエストを記録 | `file://` 以外への要求 **0件** |

テストは「ルールを追加したらテストも追加される」ことを機械的に担保している。
`SPAN_RULES` の全IDがフィクスチャに含まれているかを検証するメタテストがあり、
さらに**修正候補を適用すると同じ指摘が再発しない／別の重い指摘を生まない**ことを全ルールで確認している
（提案が自己矛盾しないことの保証）。丁寧に書けた模範メールで重要度「高」「中」が0件であることを
誤検出防止コーパスとして固定し、R1〜R5 にはそれぞれ回帰テストを追加した。

## 5. 既知の限界

- ルールベースのため指摘は網羅的ではない。文法的に正しくても意味が伝わらない文は検出できない。
- 件名には専用の4チェックのみで、敬語ルールは適用されない（FUT-01）。
- 誤検出はゼロにできない。そのために「無視」があり、重要度を色だけでなく文字でも示している。
