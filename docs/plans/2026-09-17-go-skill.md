# `/go` スキル 実装計画

> **実装者へ:** 本計画は `executing-plans` スキルに従ってタスク単位で実装すること。
> ステップはチェックボックス（`- [ ]`）で進捗を管理する。

**ゴール:** スマホから `/go -m <一言>` の1コマンドで開発に着手でき、以降の応答が画面1つ分に収まるようにする。

**構成:** `.claude/skills/go/` を新設する。`SKILL.md` が `-m` の判定とルーティングだけを担い、
モバイル時の応答規約は `references/mobile-contract.md` に分離する。
7リポジトリで同一内容を維持する（既存の共通スキルと同じ運用）。

**技術スタック:** Claude Code のスキル機構のみ。ビルド・依存追加なし。Markdown と YAML frontmatter だけ。

**設計文書:** `docs/specs/2026-09-16-mobile-dev-entry-design.md`

**検証コマンド:** 本スキルは Markdown のみで、ビルドもテストランナーも使わない。検証は4層で行う。

| 層 | 何を確かめるか | どこ |
|---|---|---|
| 構造 | frontmatter が規約どおりで、相対参照が解決する | タスク1 ステップ2（スクリプト全文あり） |
| 登録 | `go` がセッションのスキル一覧に現れる | タスク1 ステップ3 |
| 振る舞い | 応答が15行以内・番号選択肢・ゲート維持 | タスク2（実際に起動して確認） |
| 同一性 | 7リポジトリでバイト単位に一致する | タスク3 ステップ2（`sha256sum`） |

**振る舞いは自動テストで代替できない。** 検証対象がエージェントの応答の形であるため、
SKILL.md を grep しても「ソースがソースであること」しか証明できない。

## 全体制約

- スキル名は `go`。`/new` `/review` `/status` は組み込みコマンドと衝突するため使用禁止
- `disable-model-invocation: true` を必ず設定する（Claude の自動起動による循環を防ぐ）
- 既定はフル応答。`-m` 指定時のみモバイルモード
- **品質ゲート（承認・TDD・検証）を通さずに実装へ進ませない。** モバイルモードで変わるのは承認の実施方法のみ
- モバイルモードの持続はコンテキスト依存。恒久的なセッション状態は持てない
- 7リポジトリの `.claude/skills/go/` はバイト単位で同一であること
- 対象7リポジトリ: game-apps / daily-useful-tools / web-sites / dxworkrepository / kouritsu-apps / app_oshikatsu / syakai-hackathon
- ブランチは全リポジトリ `claude/superpowers-repo-integration-yrz81j`

# go — 開発の起動口

## 手順

### 1. `-m` を判定する

`$ARGUMENTS` に `-m` または `--mobile` が含まれていれば**モバイルモード**。
それを取り除いた残りを「依頼内容」として扱う。

モバイルモードなら、**この時点で `references/mobile-contract.md` を読み、
以降そのセッションの全応答でその規約を守る。**
解除するのは、人間が「通常モードで」と明示したときだけ。

宣言する:「モバイルモードで進めます。以降は短く返します。」

### 2. 依頼内容を振り分ける

| 依頼の性質 | 入るスキル |
|---|---|
| 新しく作る / 機能を追加する / 挙動を変える | `brainstorming` |
| 動かない / エラーが出る / テストが落ちる / CI が赤い | `systematic-debugging` |
| レビュー指摘・bot 指摘・CI 失敗への「対応」 | `review-triage` |
| 既存の実装計画（`docs/plans/`）の続きを実装する | `executing-plans` |
| 上のどれとも判別できない | **推測せず、番号付き選択肢で聞く**（下記） |

判別できないときは、こう聞く。

```
どれに近いですか。
1. 新しく作る・機能を足す
2. 動かないものを直す
3. レビュー指摘・CI の対応
4. 前回の続き
```

### 3. 依頼内容が空のとき

`/go` だけが送られた場合、**推測して動かない。** こう返す。

```
何をしますか。一言で教えてください。
（例: 「家計簿をCSVで読むツール」「ゲームが起動しない」「CIが赤い」）
スマホからなら -m を付けてください: /go -m <やりたいこと>
```

# モバイル契約 — スマホから使うときの応答規約

**読むタイミング:** `/go -m` が指定されたとき。以降そのセッションの全応答に適用する。

## 前提

スマホでは、長文の読解と自由記述の返信が高コストになる。
**減らすのは1往復あたりの情報量であって、品質ゲートではない。**

## 6つの規約

1. **1返信は15行以内。**
   超える内容はファイルか PR に置き、チャットには要約だけを出す

2. **質問は必ず番号付き選択肢にする。**
   自由記述を要求しない。`1` や `ok` の一言で返せること

3. **設計提示は箇条書き5行 + 選択肢。**
   ```
   1 = このまま進める
   2 = ここを直したい
   3 = もっと詳しく
   ```

4. **承認ゲートは維持する。**
   減らすのは文字数であって関所ではない。承認前にファイルを編集しない

5. **承認後は完走する。**
   逐次報告をしない。最後に PR リンクと検証結果だけを返す

6. **コードブロックをチャットに貼らない。**
   `path/to/file.ts:42` のようにファイルパスと行番号で示す

## 承認の取り方

`brainstorming` の Architectural 経路は本来「設計を節に分けて、節ごとに承認」を求める。
**モバイルモードではこれを「重要な分岐点ごとの承認」に置き換える。**

- 設計文書は通常どおり `docs/specs/` に書く（**省略しない**）
- チャットには「**決め打ちした重要な分岐を最大3点**」＋選択肢だけを出す
- **分岐が4点以上あるなら、1回のスマホ作業には大きすぎる。分割を提案する**

これはゲートの撤廃ではなく実施方法の変更である。
節ごと承認の目的は「長い設計を読める単位に割る」ことだが、
スマホでは往復が増えるほど読まれなくなり、目的を裏切る。
分岐点に絞ることで、目的（誤った前提を実装前に捕まえる）を保ったまま往復数を減らす。

## 完了報告の形

```
PR #<番号> <URL>
検証: <実行したコマンド> → <結果>
プレビュー: <プロジェクト名> (<rootDirectory>/) <URL>
未検証: <確認できなかった項目と確認手順>
```

`verification-before-completion` の要求は一切変わらない。
**実行していないコマンドの結果を書かない。** 確認できなかったものは「未検証」の行に書く。

### プレビュー URL の選び方

静的サイトのブラウザ実機確認は、本環境からもスマホからも実行できない。
Vercel のプレビュー URL があれば、それを人間がタップして確認する。

**1リポジトリに複数の Vercel プロジェクトがあり、それぞれ `rootDirectory` が異なる。**
URL を1本貼るだけでは、変更した箇所のプレビューとは限らない。

1. PR の vercel[bot] コメントからプロジェクト一覧を読む
2. **変更したパスを含む `rootDirectory` を持つプロジェクト**を選ぶ
3. プロジェクト名と `rootDirectory` を添えて URL を示す
4. **判定できないとき（該当が複数ある等）は、推測で1本選ばず候補を並べて聞く**

vercel[bot] のコメントが無いリポジトリ（`app_oshikatsu` / `web-sites` / `dxworkrepository`）では、
プレビュー行を出さず「未検証」と明示する。

**URL を貼ることと、動作を確認したことは別である。** URL があるだけで「動きます」と書かない。


## やってはいけないこと

- 短くするために**承認を飛ばす**
- 短くするために**検証を省く**
- 短くするために**「たぶん動きます」で済ませる**
- 15行に収めるために**未検証の項目を報告から落とす**

行数制限は、**省いてよい理由にならない**。
収まらないなら、内容をファイルに置いてリンクを返す。
