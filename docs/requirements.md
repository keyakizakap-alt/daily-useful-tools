# つなぎやすみ — 要件定義書

> とびとびの休みを、つないで見る。

有給休暇を「いつ・何日」取れば、手持ちの日数で一番よく休めるかを、
祝日・週休・会社の休業日から**計算して**示すブラウザアプリ。

- ステータス: MVP（2026-09-21 策定）
- 配置: `/yasumi/`（単一 HTML。ビルド済みファイルを配信）
- ソース: `src/`（本アプリの真のソース。`tools/build.mjs` が単一 HTML を生成）

### 1.2 アイデア出し（抜粋）

進行役が「日本の日常で、毎年必ず困るのに、手元で解決できていないこと」を条件に発散。

| 案 | 内容 | 評価 |
|---|---|---|
| ゴミ出し通知 | 自治体別の収集日 | 却下。自治体データの収集と維持が本体になり、静的アプリで完結しない |
| 冷蔵庫レシピ | 残り物から献立 | 却下。外部 API と API キーが必要。「機密情報を持たない」方針と衝突 |
| ふるさと納税の限度額 | 年収から控除上限を算出 | 却下。税額計算の誤りが金銭的実害に直結。MVP で背負う責任が重すぎる |
| 和暦・年号変換 | 元号の相互変換 | 却下。既存の代替が多く、斬新さがない |
| **有給の連休プランナー** | 祝日と週休の隙間を埋めて連休を作る | **採択** |

### 1.3 採択案への各観点からの意見

**一般B（課題の実在）**
> 「有給が残っているのは知っている。でも『いつ取るのが得か』を考えるのが面倒で、
> 結局そのまま消滅する。年末に気づいて慌てて消化するのが毎年の恒例。」

進行役: 厚生労働省の就労条件総合調査でも取得率は 6 割台で推移しており、
「取れない」だけでなく「取り時が分からない」層が一定数いる、という前提を採る。

**ヘビーC（差別化の核心）**
> 「この手のツールは大体『土日祝休み』決め打ち。シフト勤務だと全く使えない。
> 週休が水・木の人間が連休を作りたいときこそ計算が要るのに。」

→ **週休曜日を自由に設定できることを必須要件とする。** これが既存の類似ツールとの一番の違いになる。

**初心者A（受け入れやすさ）**
> 「設定項目が多いと、最初の画面で諦める。開いた瞬間に『今年はここが狙い目』が
> 出ていて、細かい設定は後からいじれる、という順番にしてほしい。」

→ 初期状態（土日祝休み・有給5日・当年）で**何も入力せずに結果が出ている**こと。設定は折りたたみ。

**技術D（構成）**
> 「既存2アプリと同じく、依存ライブラリなし・単一 HTML・サーバ不要を踏襲する。
> ただし祝日計算と最適化はロジックが厚い。HTML に直書きすると誰もテストできない。
> ソースを `src/lib/` のモジュールに分け、ビルドで単一 HTML に埋め込む形にしたい。」

**技術E（正しさ）**
> 「祝日は『2月11日は建国記念の日』程度の話ではない。振替休日は連鎖するし、
> 国民の休日（祝日に挟まれた平日）がある。春分・秋分は近似式で、将来は保証されない。
> **ここは必ず実データで突き合わせるテストを書く。** 提案アルゴリズムも、
> 小さい入力なら総当たりで最適解が出せるので、総当たりとの一致をテストにする。」

**設計F（情報設計）**
> 「出すべきは3つ。①今年すでにある連休、②有給を何日足すとどう伸びるかの**費用対効果ランキング**、
> ③予算内での推奨プラン。特に②の『有給1日で5連休』という言い方が、一番行動につながる。」

**設計G（アクセシビリティ）**
> 「色だけで『休日／おすすめ』を区別しない。文字と記号を併用する。
> カレンダーの日はキーボードで操作でき、読み上げで『10月13日 火曜日 有給の候補』と分かること。
> スマホの縦画面で12か月を並べるなら、横スクロールではなく段組みで折り返す。」

**安全H（データ）**
> 「勤務日・休業日・有給残日数は、その人の勤務先が推測できる情報になりうる。
> **一切外部に送らない。** 保存は localStorage のみ。アナリティクスも入れない。
> 『送信していない』ことを画面に明記し、README にも書く。」

**安全I（実装）**
> 「入力は全部自分のものだから安全、と思うのが一番危ない。
> localStorage の中身は改竄可能な外部入力として扱い、読み込み時に検証する。
> 会社休業日のラベルはユーザー入力で、DOM と .ics の両方に出る。
> DOM は textContent、.ics は RFC 5545 のエスケープを通す。
> 外部フォントも読まないことにして、CSP を `default-src 'none'` で締められる。」

### 1.4 確定事項

- 作るもの: **つなぎやすみ** — 有給休暇の連休プランナー
- 必須の差別化: シフト勤務（任意の週休曜日）対応 / 費用対効果ランキング / 完全オフライン
- 見送り（MVP 非対象）: 複数人の休み調整、勤怠システム連携、有給の付与日数の自動計算、旅行先の提案

## 2. ターゲットと課題

| ペルソナ | 状況 | 現状の困りごと | 本アプリでの解決 |
|---|---|---|---|
| 一般B（土日祝休み） | 有給が10日以上残っている | 取り時が分からず年度末に消滅 | 年間の狙い目を効率順に提示 |
| ヘビーC（シフト勤務） | 週休が平日2日 | 既存ツールが土日祝前提で使えない | 週休曜日を任意に設定して計算 |

## 3. ユースケース

### UC-1: 今年の狙い目を知る（初回・無設定）
1. ユーザーが `/yasumi/` を開く
2. アプリは当年・土日祝休み・有給5日の初期値で計算し、結果を表示する
3. ユーザーは「有給1日で5連休」の行を見て、その日付を確認する

**受け入れ条件**: 初回表示で入力操作なしに推奨プランと効率ランキングが出ている。

### UC-2: 勤務形態を自分に合わせる
1. 「休みの曜日」で水・木にチェック、土日のチェックを外す
2. 「祝日も休み」のチェックを外す（シフト勤務のため祝日は出勤）
3. 結果が即座に再計算される

**受け入れ条件**: 週休曜日と祝日の扱いを変更すると、連休・推奨プランが再計算される。

### UC-3: 会社の休業日を足す
1. 「会社の休業日」に `2026-12-29`〜`2027-01-03`（ラベル: 年末年始）を追加
2. 年末年始をまたぐ連休が結果に反映される

**受け入れ条件**: 期間指定の休業日を複数登録でき、年をまたぐ連休も正しく数える。

### UC-4: 推奨を手直しする
1. 推奨された有給日のうち、都合の悪い1日をカレンダー上でクリックして外す
2. 別の日をクリックして有給に加える
3. 上部のサマリー（連休数・最長連休・使用日数）が即時更新される

**受け入れ条件**: 任意の勤務日を有給としてトグルでき、予算超過時は警告を出す（操作はブロックしない）。

### UC-5: カレンダーに取り込む
1. 「.ics をダウンロード」を押す
2. 選択中の有給日が終日予定として書き出される
3. Google カレンダー等にインポートできる

**受け入れ条件**: 選択日がすべて終日イベントとして含まれ、RFC 5545 準拠（CRLF・75オクテット折返し・エスケープ）である。

### UC-6: 設定を残す
1. 設定を変更して離脱し、後日同じブラウザで開く
2. 前回の設定（年・週休・祝日・休業日・有給日数・手動選択・テーマ）が復元される

**受け入れ条件**: localStorage のみで復元する。壊れた値が入っていても初期値で安全に起動する。

## 4. 機能要件

| ID | 要件 | 優先 |
|---|---|---|
| F-01 | 2020〜2050 年の国民の祝日・振替休日・国民の休日を算出する | 必須 |
| F-02 | 週休曜日（7曜日の任意の組み合わせ）を設定できる | 必須 |
| F-03 | 祝日を休みとするかを切り替えられる | 必須 |
| F-04 | 会社独自の休業日を期間＋ラベルで登録できる | 必須 |
| F-05 | 有給の予算日数（0〜40）を設定できる | 必須 |
| F-06 | 既存の連休（3日以上）を一覧表示する | 必須 |
| F-07 | 有給1日あたりの効果（効率）でランキング表示する | 必須 |
| F-08 | 予算内で最適な取得日の組み合わせを提案する | 必須 |
| F-09 | 年間カレンダーで休日・祝日・有給候補を色＋記号で表示する | 必須 |
| F-10 | カレンダー上で有給日を手動トグルできる | 必須 |
| F-11 | 選択した有給日を .ics で書き出せる | 必須 |
| F-12 | 設定を localStorage に保存・復元・リセットできる | 必須 |
| F-13 | ねらい（連休の数を増やす／最長連休を伸ばす）を切り替えられる | 推奨 |
| F-14 | ライト/ダークテーマ（OS 追従＋手動） | 推奨 |
| F-15 | 祝日が未確定な年（翌々年以降）には注意書きを出す | 必須 |

## 5. 非機能要件

| ID | 要件 |
|---|---|
| N-01 | 外部通信を一切行わない（フォント・解析・API を含む） |
| N-02 | 依存ライブラリなし。単一 HTML をブラウザで開くだけで動く |
| N-03 | 再計算はユーザー操作から 100ms 以内に完了する（1年分・予算40日） |
| N-04 | キーボードのみで全操作が可能。色以外の手がかりを併記する |
| N-05 | モバイル（375px 幅）で横スクロールなしに読める |
| N-06 | 機密情報・資格情報をコードに含めない |
| N-07 | 祝日ロジックは公表値との一致をテストで担保する |

## 6. 非ゴール

- 勤怠・人事システムとの連携、複数人のスケジュール調整
- 有給付与日数・時効の自動計算（労務判断は行わない）
- 祝日の法令改正の自動追従（改正時はコード更新で対応する）
- 旅行先・料金の提案

- [ ] `npm audit` が脆弱性 0 件

## 8. 既知の制約（ユーザーに明示する）

1. 春分の日・秋分の日は近似式で算出しており、1980〜2099 年の範囲外は保証しない。
2. 国民の祝日は前年2月の官報で確定する。翌々年以降の表示は現行法に基づく**予測**である。
3. 本アプリは労務上の助言ではない。実際の取得可否・付与日数は勤務先の規程に従うこと。
