# やすみつなぎ — 要件定義書

> その1日で、何日つながる？

有給休暇を「何日休むか」ではなく「**どこに置くと連休が最長になるか**」から考えるための、
完全オフラインの連休設計ツール。

- 版: v1.0 (MVP)
- 作成日: 2026-09-14
- 対象プロジェクト: `keyakizakap-alt/daily-useful-tools`
- 収録パス: `src/`（`src/index.html` を開くだけで動作）

### 1.2 議論ログ（要約）

**PM**: 既存収録は「こいのかたち」（診断）と「そらならべ」（天気）。日常の"困りごと"寄りが薄い。
リポジトリの既存 PR には家計・調理段取り・表記ゆれ等がすでに並んでいるので、それらと被らない題材を選びたい。

**U2**: 困っているのは有給。2019年から**年5日の取得が義務**になったのに、期末に「あと3日残ってます」と
言われて雑に取る。どう置けば得なのか毎回カレンダーを指で数えている。

**U1**: 私は逆で、「飛び石連休のときに1日休めば4連休になる」というのを人から聞いて初めて知った。
自分では気づけない。**答えを出してくれる**なら使う。

**U3**: 「祝日カレンダー」は無数にあるが、**有給の最適配置**を出すものは見たことがない。
年間の残日数を入れて「この3日を使うと合計○日の連休が○回できる」まで出れば完全に実用。
出せたら ics でカレンダーに流し込みたい。

**PM**: 題材確定。**有給休暇の最適配置による連休設計ツール**。名前は「やすみつなぎ」。

**A1**: 祝日はアルゴリズムで完全に計算できる（祝日法）。外部 API もデータファイルも不要 →
このリポジトリの「依存なし・通信なし・単一ディレクトリ」の作法にそのまま乗る。
ただし**振替休日**と**国民の休日**（挟まれた平日）は連鎖するので、素朴な実装だと必ず間違える。

**A2**: 危険なのは2つ。(a) **春分・秋分**は近似式（1980–2099 で有効）であり、法的には前年2月の官報告示で確定する。
(b) `new Date("2026-09-14")` は UTC 解釈、`new Date(2026,8,14)` はローカル解釈で、混ぜると日付が1日ずれる。
→ 日付は「`YYYY-MM-DD` 文字列 + UTC 正午基準の内部表現」に統一し、**タイムゾーンを変えてもテストが通ること**を
CI 相当のコマンドで担保する。

**D1**: 入力項目は最大4つまで。初期表示は「今日から1年・有給3日・土日休み」で**何も入力しなくても答えが出ている**状態にする。
「使う有給日数」はスライダー1本。会社の休業日（年末年始・夏季）は"任意の追加入力"に落とす。

**D2**: 出力は3層。①いちばん効率のいいプラン（カード）②年間プラン（非重複の組み合わせ）③年間カレンダー。
色だけで「祝日／有給／週休」を区別しないこと（記号と凡例を併記）。カレンダーは表として読み上げ可能にし、
キーボードだけで全操作できること。ダークモード必須（既存2アプリと揃える）。

**S1**: 通信ゼロを"方針"ではなく**構造**で担保したい。外部フォント・CDN・解析タグを一切置かず、
`connect-src 'none'` を含む CSP を meta で宣言する。npm 依存は 0 個にして、サプライチェーン攻撃面を物理的に消す。

**S2**: 出力経路が1つある。**.ics エクスポート**だ。ユーザーが入力した休業日メモがそのまま ics に入ると、
`SUMMARY` フィールドで改行注入（CRLF）して偽イベントを増やせる。RFC 5545 のエスケープ（`\` `;` `,` 改行）と
制御文字の除去を**ライブラリ側で強制**し、単体テストで injection ケースを回すこと。
あと画面描画は `innerHTML` 禁止・`textContent` のみ。これは静的解析で機械的に落とす。

**U3**: 設定は保存してほしい。**S2**: 保存するのは設定だけ（有給日数・週休曜日・休業日）。
個人情報は持たない。localStorage は暗号化されないので、共有PCを想定して**保存データを消すボタン**を必ず置く。

**U1**: 「この日は本当に休みですよ」と信じすぎるのが怖い。**S1/A2**: 画面に
「祝日は祝日法に基づく計算値。春分・秋分と将来の法改正は確定値と異なる場合がある」と明示し、
根拠（何の祝日か、振替か、国民の休日か）を必ず添えて表示する。

**D1**: 「効率」という言葉が伝わらない。**U1**: 「有給1日あたり何日休めるか」と書いてあれば分かる。
→ 指標名は「**1日あたり**」（= 連休日数 ÷ 使う有給日数）とする。

### 1.3 確定した意思決定

| # | 決定 | 理由 | 反対意見の扱い |
|---|---|---|---|
| 1 | 題材は「有給の最適配置による連休設計」 | 年5日取得義務という制度的な追い風があり、既存 PR と題材が重複しない | — |
| 2 | 祝日は計算で生成（データファイル・API なし） | 依存ゼロ・通信ゼロを構造で担保 | 春分/秋分の近似は注記＋計算根拠の表示で対応 |
| 3 | 対応範囲は 2007–2099 年 | 2007年に振替休日の規定が現行（「その後の最も近い平日」）になった | 2007年以前は入力段階で範囲外として拒否 |
| 4 | ロジックは UMD 形式の素の JS に分離 | ブラウザは classic script、Node は `require` で同一コードをテスト可能。`file://` でも動く（ES module だと CORS で動かない） | ビルド工程の追加は却下（既存リポの作法に反する） |
| 5 | .ics エクスポートを MVP に含める | U3 の採用条件。かつセキュリティ上の主戦場を最初から潰すため | 生成は全てクライアント内、ダウンロードのみ |
| 6 | npm 依存は 0 個 | サプライチェーン攻撃面の排除。テストは Node 標準 `node --test` | テストフレームワーク導入は却下 |

## 2. 解決する課題

| 課題 | 現状 | 本ツール |
|---|---|---|
| 有給をどこに置くと得か分からない | カレンダーを指で数える／勘で取る | 期間内の全候補を総当たりで評価し、効率順に提示 |
| 年5日の取得義務を消化しきれない | 期末に慌てて取得 | 予算日数内で**非重複**の年間プランを自動編成 |
| 飛び石連休に気づけない | 知っている人だけが得をする | 「1日で4連休」候補を明示 |
| 振替休日・国民の休日を読み違える | 祝日一覧を目視 | 祝日法の規定どおりに連鎖計算し、根拠を表示 |
| 会社独自の休業日が計算に入らない | 手計算 | 任意の休業日／出勤日を追加入力できる |

## 3. スコープ

### 3.1 MVP に含む（v1.0）

1. 指定期間（最大 366 日）の休日判定
   - 国民の祝日（祝日法、2007–2099）
   - 振替休日（日曜と重なった祝日 → その後の最も近い非祝日）
   - 国民の休日（前後を祝日に挟まれた平日）
   - 週休（曜日単位で任意指定。既定は土日）
   - 会社休業日・特別出勤日（日付で任意に上書き）
2. 単発プラン探索: 有給を n 日（1 ≤ n ≤ 予算）使ってできる連休候補の列挙と、
   「1日あたり」（連休日数 ÷ 有給日数）による順位付け
3. 年間プラン編成: 予算日数を配分し、重複しない連休群の合計日数を最大化（動的計画法）
4. 有給ゼロでできる既存の連休（GW・シルバーウィーク等）の一覧
5. 年間カレンダー表示（休日の種別を記号＋色で区別、根拠をツールチップ/一覧で表示）
6. .ics エクスポート（プラン単位／年間プラン一括）
7. 設定の localStorage 保存と明示的な消去
8. ライト／ダークテーマ、レスポンシブ、キーボード操作、スクリーンリーダー対応

### 3.2 MVP に含まない（非ゴール）

- 半休・時間単位年休の扱い
- 有給の付与日数・時効（2年）・繰越の管理、残日数の自動計算
- 勤務シフト表（週単位でない不規則勤務）の取り込み
- 会社の休暇申請システムとの連携、サーバー保存、複数人の調整
- 交通費・宿泊費・混雑予測などの旅行計画支援
- 2007年より前の年の祝日

## 4. 想定ユーザーとユースケース

### UC-1: 残った有給を効率よく使う（U2 / 一般）
1. 画面を開く（既定: 今日から1年・有給3日・土日休み）
2. スライダーで残日数を 3 に合わせる
3. 「効率のいいプラン」に「9/18(金) を1日 → 9/19〜9/23 の5連休（1日あたり 5.0日）」が並ぶ
4. 気に入ったプランの「.ics」を押し、カレンダーに取り込む

**受け入れ条件**: 入力0回で結果が出る。上位プランは実際に休日が連続していること。

### UC-2: 年間の有給5日を計画する（U1 / 初心者）
1. 「年間プラン」タブを開く
2. 予算 5 日で「合計 21 日の休みを 4 回」といった編成が提示される
3. 各回の内訳（使う日・つながる範囲・根拠）が日本語で読める

**受け入れ条件**: 選ばれたプラン同士が日付で重複しない。使用日数の合計が予算を超えない。

### UC-3: 会社の夏季休業を加味する（U3 / ヘビー）
1. 「会社の休業日」に `2026-08-13, 2026-08-14` を追加
2. 「特別出勤日」に土曜出勤日を追加
3. 再計算され、休業日の前後をつなぐプランが上位に来る

**受け入れ条件**: 追加した休業日が休日として、特別出勤日が勤務日として扱われる（特別出勤日が優先）。

### UC-4: 祝日の根拠を確かめる（U1 / 慎重派）
1. 「年間カレンダー」で 2026-09-22 を見る
2. 「国民の休日（前後を祝日に挟まれた平日）」と表示される

**受け入れ条件**: 振替休日・国民の休日に、その理由が併記される。

### UC-5: 共有PCで使った後に痕跡を消す
1. 「保存データを消す」を押す
2. localStorage の当アプリのキーが消え、次回は既定値で開く

**受け入れ条件**: 消去後にリロードしても入力内容が復元されない。

## 6. 非機能要件

| ID | 要件 | 検証方法 |
|---|---|---|
| NFR-01 | 外部通信を一切行わない（フォント・CDN・解析を含む） | 静的解析で `fetch`/`XMLHttpRequest`/`http(s)://` 参照を検出、CSP `connect-src 'none'` |
| NFR-02 | npm 依存 0 個 | `package.json` に dependencies なし、`npm audit` |
| NFR-03 | `file://` でダブルクリック起動できる | Chromium で `file://` 読み込み時のコンソールエラー 0 件 |
| NFR-04 | 366 日分の再計算が 100ms 未満 | 計測テスト |
| NFR-05 | タイムゾーンに依存しない（UTC / Asia/Tokyo / America/Los_Angeles で同一結果） | 3 TZ でテスト実行 |
| NFR-06 | `innerHTML` / `eval` / `document.write` を使わない | 静的解析で機械的に検出 |
| NFR-07 | 色のみに依存せず情報を伝える | 記号・凡例・`aria-label` の併記 |
| NFR-08 | キーボードのみで全機能を操作できる | 手動確認＋フォーカス可視化 |

## 7. セキュリティ要件（詳細は `docs/architecture.md`）

| ID | 要件 |
|---|---|
| SEC-01 | 秘匿情報をコードに含めない（`.env` は `.gitignore` 済み。本アプリはそもそも鍵を使わない） |
| SEC-02 | 全ての DOM 書き込みを `textContent` / `createElement` で行う（XSS 経路を作らない） |
| SEC-03 | .ics 生成時に RFC 5545 のエスケープ（`\` `;` `,` 改行）と制御文字除去を強制する（ICS インジェクション対策） |
| SEC-04 | meta CSP で `default-src 'none'` を基点に、必要最小限のみ許可する |
| SEC-05 | localStorage に保存するのは設定値のみ。個人情報を保存しない。消去手段を提供する |
| SEC-06 | 不正な保存データ・不正な入力で例外を投げず、既定値へ安全に復帰する |
