### 1.3 採択案 E への議論

- U1「敬語が合っているか毎回不安で、送信ボタンの前で5分固まる。『了解しました』が失礼だと最近知った」
- U2「日に20通。1通1分の確認でも20分。指摘を**その場で置換**できないと使わない」
- U3「取引先に『至急ご対応ください』と書いて角が立ったことがある。**圧の強さ**も見てほしい」
- D1「主役は本文テキストエリア。結果は横に並べ、指摘クリックで本文の該当箇所が光る。スコアは減点ではなく『残り何点直せるか』の提示に」
- D2「重要度は色だけで区別しない（色覚多様性）。ラベル文字とアイコン形状も変える。結果件数は `aria-live` で読み上げる」
- A1「ルールデータと判定ロジックを UI から完全に分離すれば、ルール追加が UI 変更なしで済む。ブラウザからもテストからも同じコードを読む形にする」
- A2「判定は純粋関数（入力文字列 → 指摘配列）に寄せる。そうすればビルド不要・依存ゼロで単体テストできる」
- S1「**最大の論点はここ**。メール本文は業務の機密そのもの。クラウド LLM に投げる設計なら私は反対する。完全ローカル・ネットワーク送信ゼロを製品の第一価値にすべき」
- S2「さらに『本文にパスワードを直書きしている』こと自体を検出したい。ローカル処理なら、それをやっても安全という論理的な一貫性がある」
- S2「外部フォント・外部 CDN も不可。`connect-src 'none'` を CSP で宣言し、依存パッケージはゼロにする（サプライチェーン経路を作らない）」
- U1「AI に会社のメールを貼るのは正直こわい。『送信されません』と画面に書いてあるなら使える」
- PM「決まり。**完全ローカルのルールベース点検ツール**。AI 文章生成ツールとの差別化は『機密を外に出さない』『指摘理由が説明可能』の2点」

### 1.4 確定事項

1. 名称: **おくるまえに**（既存ツールのひらがな命名に合わせる）
2. 形態: 静的 Web アプリ（`src/index.html` をブラウザで開くだけ / ビルド不要 / 依存ゼロ）
3. 通信: **一切行わない**（外部 API・外部フォント・テレメトリなし）
4. 判定: ルールベース（正規表現＋文書横断チェック）。生成 AI は使わない
5. MVP スコープ外: 辞書ベースの形態素解析、文章の自動リライト、複数言語対応、共有機能

## 2. 解決する課題

| # | 課題 | 現状の代替手段 | 本ツールの提供価値 |
|---|---|---|---|
| P1 | 敬語の誤り・二重敬語に気づけない | 都度ウェブ検索 | 送信前に一括指摘＋修正候補の1クリック置換 |
| P2 | 期限・依頼が曖昧で往復が増える | 経験と勘 | 「なるはやで」等を検出し日付明記を促す |
| P3 | 表現の圧が強く関係が悪化する | 送信後に気づく | 命令形・詰問形・断定を検出し緩衝表現を提案 |
| P4 | 宛名・結び・署名の抜け | 目視 | 文書構成の不足を機械的に検出 |
| P5 | 本文にパスワード等を直書きしてしまう | 気づけない | 機密情報らしき記述を「重要度：高」で検出 |
| P6 | 校正のために本文を外部サービスへ貼る | それ自体がリスク | ローカル完結で P1〜P5 を処理 |

## 3. ターゲットユーザーとユースケース

### UC-1 新社会人が社外メールを初めて送る（U1）
1. `src/index.html` を開く
2. 件名と本文を貼る／入力する
3. 送信相手を「社外」に設定する
4. 指摘一覧を上から読み、「置換」で修正する
5. 「本文をコピー」してメールソフトへ戻る

**受け入れ条件**: 敬語の誤り・宛名の欠落・結びの欠落がそれぞれ指摘され、修正候補が提示されること。

### UC-2 事務職が1日20通を高速に確認する（U2）
1. 本文を貼ると入力停止から約0.3秒で自動的に結果が更新される
2. 重要度「高」が0件であることを確認して送信する

**受け入れ条件**: 貼り付けから結果表示までの体感が即時であること。指摘0件が明示されること。丁寧に書けた文で誤検出（重要度「高」の誤爆）が出ないこと。

### UC-3 個人事業主が催促メールの角を取る（U3）
1. 「至急ご対応ください」「なぜご返信いただけないのでしょうか」を含む下書きを点検する
2. 圧の強い表現として指摘され、緩衝表現つきの候補に置換する

**受け入れ条件**: 詰問形・命令形・「至急」が検出され、代替表現が提示されること。

### UC-4 情報漏えいの寸止め（S1 / S2 視点）
1. 本文に「パスワードは Abcd1234 です」と書かれた状態で点検する
2. 重要度「高」で「本文に資格情報を書かない」と指摘される

**受け入れ条件**: パスワード直書き・クレジットカード番号らしき数字列（Luhn 検査通過）・12桁のマイナンバーらしき数字列・API キーらしき記述が検出されること。

### UC-5 社内の同僚宛では過剰指摘をしない
1. 送信相手を「同僚」にして「了解しました」を含む本文を点検する

**受け入れ条件**: 社外／上司宛では指摘され、同僚宛では指摘されない（相手に応じてルールが切り替わる）。

## 4. 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| FR-01 | 件名・本文を入力し、入力停止から約0.3秒で点検結果を更新する | 必須 |
| FR-02 | 送信相手（社外／上司／同僚）を選択でき、適用ルールが変わる | 必須 |
| FR-03 | 指摘は「重要度・分類・該当箇所・理由・修正候補」を持つ | 必須 |
| FR-04 | 修正候補を1件ずつ、または一括で本文へ適用できる | 必須 |
| FR-05 | 個別の指摘を「無視」でき、以後の結果から除外される | 必須 |
| FR-06 | 本文の該当箇所をハイライト表示し、指摘と相互に対応づける | 必須 |
| FR-07 | 点数（100点満点）と重要度別件数を表示する | 必須 |
| FR-08 | 引用行（`>` 始まり）は本文ルールの対象外とする | 必須 |
| FR-09 | 本文をクリップボードへコピーできる | 必須 |
| FR-10 | 例文を挿入して動作を試せる | 中 |
| FR-11 | 下書きの端末内保存は既定で無効。利用者が明示的に有効化する | 必須（S1 要求） |

## 5. 非機能要件

| ID | 要件 |
|---|---|
| NFR-01 | ネットワーク通信を一切行わない（外部フォント・CDN・API を含む） |
| NFR-02 | ランタイム依存パッケージ 0（`npm audit` の対象となる本番依存を持たない） |
| NFR-03 | `file://` で直接開いて全機能が動作する（サーバー不要） |

| NFR-06 | キーボードのみで操作可能。重要度は色のみに依存せず文字でも示す |
| NFR-07 | すべての UI 文言・メッセージは日本語 |
| NFR-08 | 秘密情報（API キー等）をソースへ書かない |

## 6. ルール分類と重要度

| 分類 | 例 | 既定の重要度 |
|---|---|---|
| security（機密） | パスワード直書き、カード番号 | 高 |
| keigo（敬語の誤り） | 了解しました、各位様 | 中 |
| double（二重敬語） | お伺いします、拝見させていただく | 中 |
| humble（尊敬・謙譲の混同） | お客様が申しておりました | 高 |
| vague（曖昧） | なるはやで、今週中 | 中 |
| tone（圧の強さ） | 至急ご対応ください、なぜ〜ないのですか | 中 |
| structure（構成） | 宛名・結び・署名の欠落、件名が空 | 高／中／低 |
| redundant（冗長） | することができます、まず最初に | 低 |
| notation（表記） | 宜しく、〜して下さい | 低 |
| consistency（文体） | 敬体と常体の混在 | 低 |

点数 = `100 −（高 × 20 ＋ 中 × 8 ＋ min(15, 低 × 3)）`（下限 0）。

「低」の減点に上限（15点）を置いているのは、表記ゆれのような軽い指摘が多い長文で点数が 0 になり、
「送ってよいのか」が読み取れなくなるのを防ぐため（レビュー R5 / D2、`feedback/review_report.md`）。
**送信可否の判断は点数ではなく「重要度：高」の件数**で行い、画面の要約文で明示する。

## 7. 受け入れテスト（Step 4 で自動化する項目）

1. 分類ごとに代表ルールが検出され、`suggestion` 適用後の文字列が期待どおりになる
2. 丁寧に書かれた模範メールで重要度「高」「中」が0件（誤検出防止コーパス）
3. 引用行の内容が検出されない
4. 送信相手による出し分け（UC-5）
5. Luhn 検査を通らない数字列はカード番号として検出しない
6. `start`/`end` が元テキストの該当部分と一致する
7. 一括適用で複数の指摘が位置ずれなく反映される
8. `<script>` を含む入力がエスケープされる
9. 10,000 文字で 200ms 未満
10. 長い行がある場合でも、その行の他の指摘が隠れない（レビュー R1 の回帰）
11. 引用行に書かれた内容を文書チェックが拾わない（レビュー R2 の回帰）
12. 本文の編集で位置が動いても「無視」が維持される（レビュー R3 の回帰）

## 8. 今後の課題（MVP のスコープ外として記録）

| ID | 内容 | 出所 | 理由 |
|---|---|---|---|
| FUT-01 | 件名にも本文と同じ敬語・表記ルールを適用する | レビュー R9（U3） | 件名は本文と位置空間が別で、ハイライトと置換の経路を二重化する必要がある。MVP の受け入れ条件外 |
| FUT-02 | 文字数カウントを書記素単位（`Intl.Segmenter`）にする | レビュー R14（U2） | 絵文字が2文字と数えられるのは表示のみの問題で、点検結果には影響しない |
| FUT-03 | 社内・社外の敬称辞書を利用者が追加できるようにする | U3 | 組織固有の呼称に対応するには保存が必要で、保存を既定 OFF とした設計方針との整合を検討する |
| FUT-04 | 指摘の「無視」を端末に記憶する | U2 | 保存方針（既定 OFF）と合わせて設計する必要がある |
