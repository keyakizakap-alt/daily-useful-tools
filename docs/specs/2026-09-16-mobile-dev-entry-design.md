# スマホからの開発起動口（`/go`）設計

**日付:** 2026-09-16
**ステータス:** ドラフト
**対象:** 全7リポジトリ共通スキル（game-apps / daily-useful-tools / web-sites / dxworkrepository / kouritsu-apps / app_oshikatsu / syakai-hackathon）

## 解決する問題

`.claude/skills/` に入れた開発スキル群は熟慮を最大化する設計になっており、
brainstorming の Architectural 経路は「質問1つずつ → 選択肢2〜3案 → 節ごとに承認 → 仕様書」を要求する。
スマホ（Claude アプリの Code タブ）からこれを回すと、長文の読解と自由記述の返信が続き、実質的に使えない。

一方で、スマホで気軽に着手できないと、思いついた改善が着手されずに消える。

## ゴール / 非ゴール

**ゴール**
- スマホから**1コマンド**で開発に着手できる
- スマホでの1往復を**画面1つ分**に収める
- **品質ゲート（承認・TDD・検証）を通さずに実装へ進ませない**
  （モバイルモードでは承認の*実施方法*だけが変わる。詳細は「承認の取り方」参照）
- PC からの開発を劣化させない

**非ゴール**
- ゲートの削減・スキップ（明確に対象外。往復数は減らすが、承認そのものは省かない）
- 定期実行の自動化（Routines）— 別テーマ。後から追加可能
- アプリ本体のスマホ対応改善 — 別テーマ
- 端末の自動判定 — **技術的に不可能**（後述）

## 受け入れ条件

- [ ] `/go <一言>` で、依頼の種類に応じた既存スキルに入る
- [ ] `/go -m <一言>` で、以降そのセッションの全応答がモバイル契約に従う
- [ ] モバイルモードで、設計提示が**15行以内**かつ**番号で返答できる**形になる
- [ ] モバイルモードでも brainstorming の承認ゲートが維持される（承認前に実装が始まらない）
- [ ] `-m` 無しの `/go` は15行制限を受けず、brainstorming の節ごと承認がそのまま適用される
- [ ] 完了報告に PR リンクと検証結果が含まれ、検証できていない項目は「未検証」と明示される
- [ ] 7リポジトリの `.claude/skills/go/` がバイト単位で同一

## 検討した選択肢

### 起動口の構成

| 案 | 利点 | 欠点 | 採否 |
|---|---|---|---|
| `/new` `/fix` `/review` の3本 | 役割が明確 | **`/new` は `/clear` の別名、`/review` は `/code-review` の別名として組み込み済み**。衝突する | ✕ |
| `/dev:new` 等の名前空間3本 | 衝突回避・役割明確 | スマホで打字量が増える。覚える対象が3つ | ✕ |
| **`/go` 1本**（本文中でルーティング） | 覚えるのは1つ。最短。衝突なし | 振り分けをスキル本文に持つ必要がある | **採用** |

### モバイルモードの切り替え

| 案 | 欠点 | 採否 |
|---|---|---|
| 端末を自動判定 | **不可能。** クラウドセッションはブラウザ・スマホアプリ・CLI のどれからでも同じに見える | ✕ |
| 既定をモバイル、`--full` で PC | PC で黙って設計が端折られる事故が起きる | ✕ |
| **既定はフル、`-m` でモバイル（セッション内持続）** | 最初の1回だけフラグが要る | **採用** |

### スマホからの動作確認

| 案 | 欠点 | 採否 |
|---|---|---|
| 含めない（未検証と明示するのみ） | スマホ側でも確かめられない | ✕ |
| **Vercel プレビュー URL を完了報告に添える** | リポジトリごとの連携状況に依存する | **採用（縮退あり）** |
| 画面内エラー表示を実装 | スコープがアプリ本体の改修に広がる | ✕（将来課題） |

## 採用する設計

### 構成

```
.claude/skills/go/
├── SKILL.md                      入口。ルーティングと -m の解釈
└── references/
    └── mobile-contract.md        モバイルモードの応答規約
```

7リポジトリで同一内容を維持する（既存の共通スキルと同じ運用）。

### `/go` の frontmatter

```yaml
---
description: 開発の起動口。作る/直す/レビュー対応を振り分け、適切なスキルに入る。-m でスマホ向けの短い応答に切り替える（そのセッション中ずっと有効）。
argument-hint: "[-m] <やりたいこと>"
disable-model-invocation: true
---
```

`disable-model-invocation: true` の理由: `/go` は人間が明示的に叩く入口である。
Claude が自動起動すると、`/go` → brainstorming → 再び `/go` という循環を招きうる。

### ルーティング

`$ARGUMENTS` から `-m` を取り除いた残りを依頼内容として解釈し、次の表で振り分ける。

| 依頼内容の性質 | 入るスキル |
|---|---|
| 新しく作る / 機能を追加する / 挙動を変える | `brainstorming` |
| 動かない / エラー / テストが落ちる / CI が赤い | `systematic-debugging` |
| レビュー指摘・bot 指摘・CI 失敗への「対応」 | `review-triage` |
| 既存の実装計画の続き | `executing-plans` |
| 判別できない | **推測せず、番号付き選択肢で聞く** |

このルーティングは CLAUDE.md の起動ルールと同じ内容である。`/go` の価値は
「取りこぼしを防ぐ確実な入口」と「`-m` の受け口」であり、判断基準を新設するものではない。

### モバイル契約（`-m` 指定時）

1. **1返信は15行以内。** 超える内容はファイルか PR に置き、チャットには要約だけを出す
2. **質問は必ず番号付き選択肢。** 自由記述を要求しない（`1` や `ok` で返せること）
3. **設計提示は箇条書き5行 + `1=このまま / 2=ここを直す / 3=もっと詳しく`**
4. **承認ゲートは維持する。** 減らすのは文字数であって関所ではない
5. **承認後は完走する。** 逐次報告せず、最後に PR リンクと検証結果だけ返す
6. **コードブロックはチャットに貼らない。** ファイルパスと行番号で示す

#### 承認の取り方（重要な変更点）

brainstorming の Architectural 経路は「節ごとに承認」を求める。
モバイルモードではこれを**「重要な分岐点ごとに承認」に置き換える**。

- 設計文書は通常どおり `docs/specs/` に書く（省略しない）
- チャットには「**決め打ちした重要な分岐を最大3点**」＋選択肢を出す
- 分岐が4点以上あるなら、それは1回のスマホ作業には大きすぎる。**分割を提案する**

これはゲートの**撤廃ではなく実施方法の変更**である。
節ごと承認の目的は「長い設計を読める単位に割る」ことであり、スマホでは往復数が増えるほど読まれなくなる。
分岐点に絞ることで、目的（誤った前提を実装前に捕まえる）を保ったまま往復数を減らす。

### 完了報告の形

```
PR #<番号> <URL>
検証: <実行したコマンド> → <結果>
プレビュー: <Vercel URL>   ← 連携がある場合のみ
未検証: <確認できなかった項目と、その確認手順>
```

`verification-before-completion` の要求は変わらない。
**実行していないコマンドの結果を書かない。** 確認できなかったものは「未検証」の行に書く。

### Vercel プレビューの扱い（縮退つき）

| リポジトリ | 現状 | 完了報告での扱い |
|---|---|---|
| daily-useful-tools / game-apps | `vercel.json` あり | プレビュー URL を添える（連携確認後） |
| kouritsu-apps / syakai-hackathon | `vercel.json` なし | 連携するまでは「未検証」と明示 |
| web-sites / dxworkrepository | 実装なし | 実装追加時に判断 |
| app_oshikatsu | Docker 構成 | 対象外（プレビュー環境なし） |

**未確認の前提:** 各リポジトリが Vercel プロジェクトに連携済みで、Preview Deployments が
有効かどうかは、リポジトリの中身からは判定できない。PR に Vercel bot のコメントが付くかで確認する。
**連携が無い場合でも `/go` は動作する**（プレビュー行を出さないだけ）。

## 制約とリスク

| 項目 | 内容 |
|---|---|
| **モード消失** | `-m` の持続はスキル本文がコンテキストに残ることに依存する。長いセッションで自動圧縮が起きるとモバイルモードが失われうる。その場合は `/go -m` を再度打つ。恒久的なセッション状態を持つ手段は無い |
| **端末判定不可** | Claude は端末を検知できない。`-m` の付け忘れはユーザ側の操作ミスとして残る |
| **ルーティングの重複** | CLAUDE.md の起動ルールと内容が重複する。片方だけ更新すると乖離する。両方の同期を運用ルールに含める |
| **Vercel 依存** | 連携状況が外部（Vercel 側の設定）に依存し、リポジトリからは検証できない |
| **スコープ拡大の誘惑** | 「画面内エラー表示」「Routines 連携」は有用だが本設計の対象外。要望が出たら別設計とする |

## 検証方法

| 受け入れ条件 | 確認方法 |
|---|---|
| `/go` が認識される | セッションのスキル一覧に `go` が現れること |
| ルーティング | `/go これ動かない` で systematic-debugging に入ること |
| `-m` の効果 | `/go -m <依頼>` の応答が15行以内かつ番号選択肢を含むこと |
| `-m` の持続 | 同一セッションの2往復目以降も15行以内であること |
| 既定がフル | `-m` 無しの `/go` が従来の詳細度で応答すること |
| ゲート維持 | モバイルモードで、承認前にファイル編集が発生しないこと |
| 7リポジトリ同一 | `find .claude/skills/go -type f \| sort \| xargs sha256sum \| sha256sum` が全リポジトリで一致 |
