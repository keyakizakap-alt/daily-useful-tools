# 設計ドキュメント - わりかんスッキリ

## 1. 全体構成

```
src/
  warikan.js   - 計算エンジン（純粋関数、UIから独立）
  app.js       - UIロジック（DOM操作、warikan.js の呼び出し）
  index.html   - 画面（日本語）
  style.css    - スタイル
tests/
  warikan.test.js - 計算エンジンの自動テスト（node:test 使用、追加依存なし）
```

UIと計算ロジックを分離することで、ロジック単体をNode.jsから直接テストできるようにする。
`warikan.js` はブラウザの `<script type="module">` からも Node.js の `node:test` からも
同一ファイルを読み込めるよう ESM 形式（`export`）で実装する。

## 2. データモデル

```js
// メンバー: 文字列の配列
const members = ["あかね", "けん", "みさき"];

// 支出: オブジェクトの配列
const expenses = [
  {
    payer: "あかね",     // 支払った人
    amount: 3000,        // 金額（円）
    participants: ["あかね", "けん", "みさき"], // 対象者。省略時は members 全員
  },
];
```

## 3. 計算アルゴリズム

### 3.1 収支（balance）の計算

各メンバーについて:
- 支払った金額の合計を加算
- 参加した支出について、その支出を参加者数で均等割りした額を減算

均等割りで端数（余り）が出る場合は、参加者のうち先頭から順に1円ずつ多く負担させることで、
合計金額と支出額が必ず一致するようにする（浮動小数点誤差を避けるため、金額は常に整数の円で扱う）。

結果として `balance[member]` は:
- 正の値 → その人は払いすぎている（他のメンバーから受け取るべき）
- 負の値 → その人は不足している（他のメンバーに払うべき）
- 合計は必ず 0 になる

### 3.2 精算リスト（最小送金回数）の計算

貪欲法（greedy algorithm）を採用する:

1. balance が正のメンバー（貸し手）と負のメンバー（借り手）に分ける。
2. 貸し手・借り手それぞれを絶対値が大きい順にソートする。
3. 最大の貸し手と最大の借り手をペアにし、min(貸し手の残額, 借り手の残額) を送金額として記録する。
4. 双方の残額を更新し、残額が 0 になった人をリストから除く。
5. 貸し手・借り手のどちらかが空になるまで繰り返す。

この方法は最小送金回数の厳密な最適解を保証するものではないが、
実務上ほぼ最小に近い件数に収束し、実装がシンプルで理解しやすいという利点がある。
（N人の完全最適化はNP困難に近い部分集合和問題になるため、MVPでは貪欲法を採用する。）

## 4. UI設計

- 1画面完結のシングルページ構成。
- 上部: メンバー登録フォーム（名前を入力して「追加」）。
- 中部: 支出登録フォーム（支払った人・金額・対象者チェックボックス・「追加」）。
  登録済みの支出は一覧表示され、削除も可能。
- 下部: 「精算する」ボタンを押すと、各メンバーの収支と、送金リスト
  （例: 「けん → あかね: 1,000円」）を表示する。
- 全てのラベル・ボタン・エラーメッセージは日本語。

## 5. テスト方針

`tests/warikan.test.js` で以下を検証する:
- 均等割りで割り切れるケースの収支計算
- 割り切れない端数が出るケースで合計が一致すること
- 一部メンバーのみが対象の支出（部分参加）の収支計算
- 精算リストの送金元・送金先・金額の妥当性（全ての送金後に全員の残高が0になること）
- メンバーが1人、支出が0件などの境界値
