# 設計ドキュメント — 段取りキッチン

## 1. プロダクト概要

複数の料理を同時に作るとき、**できあがり時刻から逆算**して
「何を、何時に、何分やるか」を1本のタイムラインに組み立てるツール。

レシピアプリは「何を作るか」「1品をどう作るか」は教えてくれるが、
**1人の調理者が複数の料理をどう並行させるか**は教えてくれない。
そこだけを解く。

## 2. 解決する課題

家庭で複数品を作るとき、次の失敗が日常的に起きる。

1. **完成時刻がそろわない** — 最初に作った料理が冷めてから、最後の料理ができあがる
2. **手が足りない瞬間が生まれる** — 3つのコンロが同時に「今すぐ手を出せ」と要求してくる
3. **放置時間が空転する** — 煮込みの20分に何もせず待ち、後半で慌てる
4. **逆算できない** — 「18時30分に食べたいなら何時に始めるか」が経験と勘に依存する

本質は「1人（または数人）という有限リソースの下でのスケジューリング問題」であり、
人間が暗算するには難しいが、計算機には向いている。

## 3. 中核となるモデル

### 3.1 工程の2分類

すべての調理工程を次の2つに分ける。この区別が本ツールの土台になる。

| 種類 | 意味 | 例 | 並行性 |
| --- | --- | --- | --- |
| **つきっきり（attended）** | 手が塞がる | 切る、炒める、盛り付ける | 同時に「調理者の人数」まで |
| **放置（unattended）** | 火にかけて離れられる | 煮る、炊く、寝かせる、冷やす | 何本でも並行可能 |

放置工程の裏につきっきり工程を差し込めることが、時短の源泉になる。

### 3.2 データ構造

```
Dish（料理）
  id           一意なID
  name         料理名
  steps        調理順に並んだ工程の配列
  holdMinutes  完成後に置いておける時間（分）
               0 = できあがり時刻ちょうどに熱々で出したい
               45 = サラダのように45分前に作っておいてよい

Step（工程）
  name      工程名
  minutes   所要時間（0以上の整数・分）
  attended  つきっきりなら true、放置なら false
```

### 3.3 offset という座標系

計算はすべて **offset（できあがり時刻の何分前か）** で行う。

- できあがり時刻そのものが `offset = 0`
- **offset が大きいほど時間的に早い**
- 実時刻への変換は `実時刻 = targetTime - offset`

「逆算」という問題の性質に座標系を合わせることで、
日をまたぐ場合（前日23:40開始など）も負の実時刻として自然に扱える。

## 4. 中核アルゴリズム

### 4.1 逆算スケジューリング（後ろ向きリストスケジューリング）

**入力**: 料理の配列、できあがり目標時刻 `targetTime`、調理者の人数 `cooks`
**出力**: 全工程の開始・終了時刻、調理開始時刻、総所要時間

---

**手順1: 理想 offset の算出（リソース競合を無視）**

各料理について、最後の工程から前に向かって積み上げる。

```
最後の工程の終了 offset = dish.holdMinutes
工程 i の開始 offset    = 工程 i の終了 offset + 工程 i の所要時間
工程 i の終了 offset    = 工程 i+1 の開始 offset
```

この時点では「全料理が理想どおりに並行できる」という前提の、
最も遅く始められるスケジュール（最遅開始）が得られる。

---

**手順2: つきっきり工程の抽出**

全料理から `attended === true` かつ `minutes > 0` の工程を集める。
所要時間0分の工程はリソースを占有しないため対象外とする。

---

**手順3: 競合の解消（後ろから確定させる）**

未確定のつきっきり工程のうち、**終了 offset が最小のもの**
（＝時間的に最も遅いもの）から順に確定させる。
盛り付けなど提供直前の工程を優先して固定し、手前の工程を前倒ししていく。

確定させようとする工程 `s` について、次を繰り返す。

```
1. 確定済みの工程のうち、s と時間的に重なるものを集める → overlapping
   （重なりの判定: other.終了offset < s.開始offset かつ s.終了offset < other.開始offset）

2. overlapping の本数が cooks 未満なら、競合なし → s を確定して終了

3. 競合している場合、重なりを cooks-1 本まで減らすには、
   overlapping のうち開始 offset が小さい方から (本数 - cooks + 1) 本を追い越す必要がある。
   overlapping の開始 offset を昇順に並べ、
     新しい終了 offset = 昇順配列[本数 - cooks]
   とし、その差分 delta だけ s を前倒しする。

4. s とそれより手前（調理順で前）の同じ料理の全工程を、まとめて delta だけ前倒しする。
   → 工程の順序関係が壊れないことが保証される。

5. 手順1に戻る（前倒しによって新たな競合が生じうるため）
```

**手順3-4の正当性**: 同じ料理の手前の工程は、必ず現在の工程より
終了 offset が大きい（＝処理順で後）。したがって前倒し対象の工程が
すでに確定済みであることはなく、確定済みの配置を壊さない。

**停止性**: 各反復で `s` の終了 offset は真に増加し、
その上限は確定済み工程の開始 offset の最大値で抑えられるため、有限回で停止する。

**計算量**: 工程数 n に対して O(n²)。家庭料理の規模（数十工程）では十分。

---

**手順4: 実時刻への変換**

```
総所要時間  = 全工程の開始 offset の最大値
調理開始時刻 = targetTime - 総所要時間
各工程の開始時刻 = targetTime - 開始 offset
```

### 4.2 手を動かす時間・手が空く時間の算出

```
手を動かす時間（activeMinutes） = つきっきり工程の所要時間の合計
のべ手待ち時間（idleMinutes）   = max(0, 総所要時間 × cooks - activeMinutes)
```

`idleMinutes` は**のべ人数分**の値であり、経過時間そのものではない。
（2人で95分調理し45分手を動かしたなら、のべ手待ちは 95×2-45 = 145分）
UI上はその旨がわかる表記にする。

### 4.3 待ち時間の検出

料理ごとに、工程間に生じた空き時間を集計する。

```
待ち時間 = Σ (工程 i の終了 offset - 工程 i+1 の開始 offset)
```

競合解消で工程が前倒しされると、その料理の後続工程との間に空きが生まれる。
これは「切った野菜が待っている」状態であり調理上は許容されるが、
15分以上になる場合は利用者に伝える。

### 4.4 タイムラインのスロット化

同時刻に始まる工程をまとめ、その時点で「裏で進行中」の放置工程を併記する。

```
スロットの開始時刻の集合 = 全工程の開始時刻の重複排除・昇順
各スロットについて:
  attended = その時刻に始まるつきっきり工程
  running  = 開始時刻 ≤ その時刻 < 終了時刻 を満たす放置工程
```

これにより「18:06 味噌汁の具材を切る（裏でごはんが炊飯中）」という表示ができる。

## 5. アーキテクチャ

```
src/
├── lib/           純関数のみ。DOM に依存せず、Node からも import できる
│   ├── time.js       時刻のパース・整形（日跨ぎ、全角数字対応）
│   ├── scheduler.js  逆算スケジューリングの中核
│   ├── recipes.js    日本の家庭料理プリセット
│   └── storage.js    直列化/復元（純粋）＋ localStorage 入出力（副作用）
└── web/           DOM の描画と入力の受け取りのみ
    ├── index.html
    ├── style.css
    └── app.js
```

**分離の方針**: 計算を `lib/` の純関数に閉じ込め、`web/app.js` は
「状態を読んで DOM を描く」だけにする。これにより中核ロジックが
ブラウザなしで完全にテストできる。

`storage.js` は直列化/復元（`serializeState` / `deserializeState`）を
純関数として切り出し、localStorage に触る部分（`saveState` / `loadState`）は
ストレージを引数で差し替えられるようにして、テストからスタブを注入できるようにした。

## 6. データモデル（localStorage）

- **キー**: `dandori-kitchen/v1`
- **値**: 次の構造のJSON文字列

```json
{
  "version": 1,
  "targetTime": "18:30",
  "cooks": 1,
  "dishes": [
    {
      "id": "dish-abc-1",
      "name": "味噌汁",
      "holdMinutes": 5,
      "steps": [
        { "name": "具材を切る", "minutes": 5, "attended": true },
        { "name": "煮る", "minutes": 7, "attended": false }
      ]
    }
  ]
}
```

`version` が一致しない場合は読み込まず既定状態で起動する。
壊れた料理・工程は復元時に取り除き、アプリが起動しなくなることを防ぐ。

## 7. 画面構成

| 領域 | 内容 |
| --- | --- |
| 条件 | できあがり時刻 / 作る人の数 / プリセットからの追加 / 自分で追加 / すべて削除 |
| 献立 | 料理カードの一覧。料理名・余裕時間・工程（名前・分・つきっきり/放置）を直接編集 |
| 段取り | サマリ（調理開始・できあがり・総所要・手を動かす時間・手が空く時間）／警告／タイムライン／料理ごとの開始・完成 |

入力のたびに再計算し、結果を即座に反映する。保存ボタンは設けず、変更時に自動保存する。

## 8. テスト戦略

| 種類 | 対象 | 内容 |
| --- | --- | --- |
| 単体テスト | `time.js` | 時刻のパース・整形、日跨ぎ、全角数字、異常系 |
| 単体テスト | `recipes.js` | プリセットの整合性、コピーの独立性 |
| 単体テスト | `storage.js` | 直列化の往復、壊れたデータの復旧、ストレージ例外時の動作 |
| 単体テスト | `scheduler.js` | 代表的な献立に対する具体的な期待値 |
| **不変条件テスト** | `scheduler.js` | ランダム生成した献立に対し、常に成り立つべき性質を検証 |
| ブラウザ検証 | `web/` | Playwright で実際に操作し、JSエラーがないこと・保存復元を確認 |

### 検証する不変条件

固定シードの疑似乱数で献立を生成し、次が常に成り立つことを確認する。

1. つきっきり工程が「調理者の人数」を超えて重ならない
2. 各料理の工程が調理順を守る（工程 i の終了 ≤ 工程 i+1 の開始）
3. どの料理もできあがり時刻までに完成する
4. 開始時刻と総所要時間が整合する（`startTime = targetTime - totalMinutes`）
5. 工程数と各工程の所要時間が入力から変化しない
6. 全工程がつきっきりなら、総所要時間は所要時間の単純合計と一致する
7. **調理者を増やすと総所要時間は決して長くならない**（単調性）

7 は最適化アルゴリズムが陥りやすい「人数を増やすと悪化する」バグを捕まえるためのもの。

## 9. スコープ外（今回作らないもの）

- コンロ・オーブンなど**器具単位の排他制御**（今回は「人」だけを有限リソースとして扱う）
- レシピの自動取り込み（URLやテキストからの工程抽出）
- 調理中の進行モード（現在時刻に追従して「次にやること」を光らせる）
- 栄養計算・買い物リスト・在庫管理
- 複数端末間の同期（localStorage のみ、通信は行わない）
- 工程間の「冷めてはいけない」制約（前倒しによる待ちを禁止する指定）

## 10. リスクと対策

| リスク | 対策 |
| --- | --- |
| 工程の所要時間を入力するのが面倒で使われない | 日本の家庭料理10品をプリセットとして同梱し、初回起動時から3品入った状態で始める |
| ヒューリスティックが最適解を出さない | 最適性は保証しない代わりに、破綻しないこと（不変条件）をテストで保証する |
| 器具の競合を見ていないため非現実的な計画が出る | スコープ外と明記。将来はリソース種別を一般化して対応する |
| localStorage が使えない環境で落ちる | 読み書きを例外安全にし、失敗時は保存せず動作を継続する |
| 前日にずれ込むほど長い献立 | 負の時刻を「前日 23:40」と表示し、警告を出す |
