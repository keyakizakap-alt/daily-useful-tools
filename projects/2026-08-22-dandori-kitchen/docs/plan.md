# 実装計画 — 段取りキッチン

## 全体方針

計算を `src/lib/` の純関数に閉じ込め、`src/web/` は描画と入力の受け取りだけにする。
これにより中核ロジックをブラウザなしで検証でき、UIの作り込みとロジックの正しさを分離できる。

## フェーズ

### フェーズ1: 基盤（時刻ユーティリティ）
- `src/lib/time.js` — パース・整形・日跨ぎ・全角数字対応
- `tests/time.test.js`
- **完了条件**: 前日・翌日にまたがる時刻が正しく表示できる

### フェーズ2: 中核アルゴリズム
- `src/lib/scheduler.js` — 逆算スケジューリング、入力検証、タイムラインのスロット化
- `tests/scheduler.test.js` — 代表的な献立に対する具体的な期待値
- `tests/scheduler.invariants.test.js` — ランダム献立に対する不変条件
- **完了条件**: つきっきり工程の重なりが人数以下であることが、ランダム入力でも成り立つ

### フェーズ3: データ
- `src/lib/recipes.js` — 日本の家庭料理プリセット10品
- `src/lib/storage.js` — 直列化（純粋）＋ localStorage 入出力（副作用、差し替え可能）
- `tests/recipes.test.js` / `tests/storage.test.js`
- **完了条件**: 壊れた保存データでもアプリが起動する

### フェーズ4: UI
- `src/web/index.html` / `style.css` / `app.js`
- **完了条件**: プリセットで3品入った状態で起動し、入力のたびに再計算される

### フェーズ5: 検証
- Playwright で実ブラウザ操作（時刻変更・人数切替・追加削除・リロード復元・スマホ幅）
- **完了条件**: JSエラーがゼロで、リロード後も状態が復元される

### フェーズ6: フィードバックと改良
- 模擬ユーザーエージェントによる試用レポートの取得
- 指摘のうち、MVPの範囲で価値の高いものを反映
- `feedback/review.md` と `feedback/iteration.md` に記録

## 実装順序の理由

スケジューラを最初に固めるのは、このアプリの価値がすべてそこに集約されるため。
UIを先に作ると「それらしく動くが実は破綻しているスケジュール」を見逃しやすいので、
不変条件テストでロジックの正しさを確定させてから画面に載せる。

## 想定した主な難所

| 難所 | 対処 |
| --- | --- |
| 工程を前倒しした際に、同じ料理の手前の工程との順序が壊れる | 前倒し時に手前の全工程を同じ分だけ一緒に動かす |
| 前倒しによって新たな競合が生じ、解決が振動する | 各反復で終了 offset が真に増加することを保証し、有限回で停止させる |
| 「人数を増やしたら遅くなる」という直感に反するバグ | 単調性を不変条件テストで明示的に検証する |
| 所要時間0分の工程がリソースを占有してしまう | 競合解消の対象から除外する |
