## 詳細

### F-1: 全削除後の復活（致命的な信頼性の問題）

**原因**: 起動時の判定が「保存された料理が**1件以上**あれば復元、なければ初期サンプルを投入」
となっていた。そのため「料理0件で保存された状態」と「一度も保存していない状態」が区別できず、
利用者が意図的に空にしても、次回起動時に初期サンプルが復活していた。

```diff
- if (restored && restored.dishes.length > 0) {
+ if (restored) {
+   // 保存データがあれば、料理が0件（利用者が意図的にすべて削除した状態）でもそのまま尊重する。
```

保存データが**一度も存在しない初回のみ**サンプルを投入するようにした。

「削除したのに戻ってくる」はデータが失われたように見え、アプリ全体の信頼を損なう。
このため、空の状態が保存・復元されることを回帰テストで固定した。

### F-2: 数値編集とボタン操作の競合

**原因**: 数値入力の `change` イベント（フォーカスが外れた時点で発火）が
献立一覧全体の再描画を引き起こしていた。利用者が数値を打ち直してすぐ同じ行のボタンを押すと、
`mousedown` と `click` の間で対象のDOMノードが作り直され、クリックが成立しなかった。
連続操作時に `replaceChildren` の例外が出ていたのも同じ原因。

**対応**: 数値の変更・種類の切り替えでは献立一覧を作り直さず、
結果の再計算（`renderResult`）と保存だけを行うようにした。
種類の切り替えボタンは、行を作り直す代わりに `aria-pressed` を直接更新する。

画面の表示は利用者が入力した値そのものなので、行を作り直す必要はもともとなかった。

### F-3: 人数を増やす意味が伝わらない

指摘は2つの問題が重なっていた。

**（1）指標名の誤り** — `idleMinutes` は `総所要時間 × 人数 - 手を動かす時間` という
**のべ人数分**の値である。2人設定では経過時間より大きくなるため、
「手が空く時間」という名前では「増えた」と誤解される。
1人のときだけ「手が空く時間」、2人以上では「のべ手待ち時間」と呼び分けるようにした。

**（2）効果が見えない** — 指摘の献立（ごはん・味噌汁・生姜焼き）は炊飯の待ち時間が
全体を決めているため、人数を増やしても総所要時間は本当に変わらない。
これは正しい計算結果だが、説明がなければ機能が壊れているように見える。

そこで、人数が2人以上のときに1人の場合のスケジュールも計算し、次のどちらかを表示するようにした。

- 短縮できる場合: 「2人で作ると、1人のときより 20分 短くなります（1人なら 40分）」
- 短縮できない場合: 「この献立では2人にしても総所要時間は変わりません。煮込みや炊飯など
  「放置」の待ち時間が全体を決めているためです。」

### F-5: 品数が増えたときの細切れなタイムライン

> 6品では24以上の時刻に分割され、2〜4分おきに違う料理の作業へ切り替わる。
> 実際にこの通りにスマホを見ながら台所仕事をこなすのは無理。

これは最短時間を求めるアルゴリズムの性質そのものであり、
「まとめて余裕を持たせる」制御を入れるのはMVPの範囲を超える。

代わりに、料理をまたぐ作業の切り替え回数を数える `countDishSwitches()` を追加し、
12回以上になる場合に品数を減らすか「できあがりの◯分前でOK」を使うよう促す警告を出すようにした。
問題を解決したわけではないが、破綻する前に気づけるようにした。

平日の3品程度では警告が出ないことも回帰テストで固定している。
