### 1.2 アイデア候補と評価

PM が「日本の生活に固有で、年に何度も発生し、いまは手作業で解かれている計算」を条件に出した。

| 候補 | U 評価 | A 評価 | S 評価 | 判定 |
|---|---|---|---|---|
| ごみ収集日カレンダー | 需要は高い | 自治体ごとのデータ収集が本体で、通信ゼロにできない | — | 却下 |
| 割り勘・精算ツール | 既存アプリが飽和 | 実装は容易だが新規性なし | — | 却下 |
| ご祝儀・香典の相場ガイド | 迷う場面は多い | データが主観的で根拠を示せない | 誤った金額を示す責任リスク | 却下 |
| 営業日・支払期日計算 | 地味だが確実 | 祝日計算が core。単体では用途が狭い | 低リスク | 保留（下の候補に内包） |
| **有給ブリッジ（連休設計）** | **U1〜U3 全員が「毎年やっている」** | **祝日計算＋組合せ最適化で、計算だけで完結** | **入力は曜日と日数のみ。個人情報を扱わない** | **採択** |

### 1.3 採択理由（PM まとめ）

- **日本固有性**: 国民の祝日に関する法律（祝日法）の「ハッピーマンデー」「振替休日」「国民の休日」という 3 つのルールが、日本の連休の形を決めている。これを正しく展開できること自体が価値になる。
- **反復性**: U2「毎年 4 月に有給付与されたあと、カレンダーを見ながら電卓で数えている」。U3「飛び石連休をつなぐ最短の有給を探すのが毎年の趣味みたいになっている」。
- **計算で閉じる**: 外部 API・サーバー・ログインが不要。通信ゼロで成立する。本リポジトリの既存アプリ（こいのかたち / おくるまえに）と同じ思想。
- **既存アプリと重複しない**: 天気（そらならべ）、学習（くもみち）、文章点検（おくるまえに）のいずれとも領域が異なる。

### 1.4 議論で決まった仕様上の論点

| # | 論点 | 発言 | 決定 |
|---|---|---|---|
| 1 | 「連休」の定義 | U1「3連休から連休と呼びたい」 | 連続 3 日以上を連休として扱う |
| 2 | 土日休み前提でよいか | U2「自分はシフト勤務で水・日休み」 | 勤務曜日を 7 曜日ぶん個別に設定できるようにする |
| 3 | 会社の独自休業日 | U2「夏季休暇と年末年始がある」 | 休業日を日付・期間で追加入力できるようにする |
| 4 | 何を最適化するか | U3「効率（連休日数 ÷ 有給日数）が見たい」／U2「年間の計画が見たい」 | **両方出す**。①効率ランキング ②有給残数内で年間プランを自動編成 |
| 5 | プランの最適化基準 | A1「貪欲法だと局所最適になる」 | 日×残日数の動的計画法で解く。評価値は「長い連休を優先（日数の二乗）」「休みの回数を優先（日数）」から利用者が選ぶ（実装時の試算で、単純な日数合計の最大化では 3 連休が多数並ぶだけになると判明したため。`docs/architecture.md` §5.3） |
| 6 | 過去日が出るのは邪魔 | U1「今日より前の提案は要らない」 | 既定の対象期間を「今日から 12 か月」とし、年指定にも切り替えられる |
| 7 | 春分・秋分の扱い | A2「暦要項は前年 2 月官報で確定。将来年は計算値」 | 近似式で算出し、**計算値である旨を画面に明示**。2026・2027 年は官報公表値と一致することをテストで固定 |
| 8 | 初見で分かるか | D1「数字の羅列では伝わらない」 | 「有給 2 日 → 9 連休」のように**投入と成果を 1 行で**見せるカード型。月カレンダーで色分けも併置 |
| 9 | 色だけで区別しない | D2「色覚特性で祝日と有給が混ざる」 | 色＋記号（●祝 / ★有給 / 休）＋凡例。コントラスト比 4.5:1 以上 |
| 10 | スマホで使えるか | U1「通勤中に見る」 | 1 カラムレイアウト、タップ領域 44px 以上、横スクロールなし |
| 11 | 入力を保存するか | S2「勤務シフトは準個人情報に近い」 | localStorage に**設定のみ**保存。氏名・会社名などの自由記述欄は設けない。1 タップで消せる |
| 12 | 外部送信 | S1「通信ゼロを設計で保証したい」 | CSP で `default-src 'none'` とし、通信経路を持たない。フォント以外の外部参照なし |
| 13 | 計画表の持ち出し | U3「申請時にコピペしたい」 | プレーンテキストでクリップボードにコピー。印刷用スタイルも用意 |
| 14 | 法的な注意 | S1「公式カレンダーと誤認されると困る」 | 非公式である旨と、確定方法（官報・就業規則）への案内を明記 |

## 2. 解決する課題

日本の会社員は、年に 1 回以上「限られた有給休暇を、どの日に置けば最も長く休めるか」を手作業で計算している。
この計算は次の 3 つが絡むため、カレンダーを眺めるだけでは最適解が出ない。

1. **祝日の位置**が年によって動く（ハッピーマンデー、春分・秋分、振替休日、国民の休日）。
2. **自分の勤務曜日**が人によって違う（土日休み／日のみ／シフト）。
3. **有給の残日数という予算**の中で、年間を通じた配分を決める必要がある（局所的に 1 か所を最大化しても、年間では損になりうる）。

やすみつなぎは、この 3 つを入力として受け取り、**有給 1 日あたりの連休効率**と**年間の最適配分**を自動で提示する。

## 3. スコープ

### 3.1 MVP に含める

- 祝日の自動展開（2016〜2099 年。山の日の施行、2019 年の即位関連、2020・2021 年の五輪特例を年ごとに切り替え）
- 振替休日・国民の休日の自動付与
- 勤務曜日設定（7 曜日を個別にオン／オフ）
- 会社休業日の追加（単日・期間）
- 有給残日数の設定（0〜40 日）
- 連休候補の列挙と効率ランキング
- 有給残数の予算内での年間プラン自動編成（動的計画法）と、優先モードの切り替え
- 有給の内訳（繰越分・今年度分）と失効日の管理、失効しそうな日数の警告
- 有給を取れない期間（繁忙期）の指定
- プランの iCalendar（.ics）書き出し
- 月カレンダー表示（祝日・休業日・有給候補を色＋記号で区別）
- プランのテキストコピー、印刷
- 設定の localStorage 保存とリセット
- ライト／ダークテーマ、キーボード操作、スマホ対応

### 3.2 MVP に含めない（将来）

- 半日有給・時間単位有給
- 年 5 日の取得義務の進捗（入力が「残日数」のため、付与日数が 10 日以上かを判定できない。
  誤った法的判断を示すより、扱わないことを選んだ）
- 他人のカレンダーとの突き合わせ（チームの休暇調整）
- 旅費・混雑度などの外部データ連携
- 会社ごとの就業規則の取り込み

## 4. ユースケース

### UC-1: 年度はじめに年間の休暇計画を立てる（U2・主要導線）

| 項目 | 内容 |
|---|---|
| 利用者 | 土日休みの会社員。4 月に有給 15 日が付与された |
| 事前条件 | なし（インストール・ログイン不要） |
| 手順 | 1. ページを開く → 2. 勤務曜日が「月〜金」でよいか確認 → 3. 有給残日数に 15 を入力 → 4. 「年間プラン」を見る |
| 結果 | 15 日の有給を複数の連休に配分した案が表示され、各連休の日数・使う有給日・効率が分かる。テキストでコピーして申請メモに貼れる |
| 代替 | 勤務曜日がシフトの場合は手順 2 で曜日を切り替える |

### UC-2: 飛び石連休をつなぐ最小の有給を知る（U3）

| 項目 | 内容 |
|---|---|
| 利用者 | 効率を最大化したい利用者 |
| 手順 | 1. 「効率ランキング」タブを開く → 2. 有給 1 日・2 日で得られる連休を上から見る |
| 結果 | 「有給 1 日 → 4 連休（効率 4.0 倍）」のように、投入 1 日あたりの連休日数が高い順に並ぶ |

### UC-3: 会社の夏季休暇を含めて数える（U2）

| 項目 | 内容 |
|---|---|
| 手順 | 1. 「会社休業日」に `8/13-8/15` を追加 → 2. 再計算 |
| 結果 | 夏季休暇が休みとして扱われ、その前後に有給を置く案が候補に入る |

### UC-4: 来年の連休の形だけ知りたい（U1）

| 項目 | 内容 |
|---|---|
| 手順 | 1. 対象期間で「2027 年」を選ぶ → 2. 有給 0 日のまま、既存の連休を見る |
| 結果 | 有給を使わずに成立する 3 連休以上がすべて表示される（根拠として祝日名も表示） |

## 5. 機能要件

| ID | 要件 | 受入条件 |
|---|---|---|
| FR-01 | 指定年の祝日を算出する | 2026 年・2027 年の全祝日が官報公表値と一致（テストで固定） |
| FR-02 | 振替休日を付与する | 祝日が日曜のとき、以後の最初の「祝日でない日」が休日になる |
| FR-03 | 国民の休日を付与する | 前日・翌日がともに祝日である平日が休日になる（例: 2026/9/22） |
| FR-04 | 年ごとの特例を反映する | 2019 年は天皇誕生日を出さず 5/1・10/22 を休日とする。2020・2021 年は五輪特例の移動日を使う |
| FR-05 | 勤務曜日を設定できる | 7 曜日を個別に設定でき、すべて休みにしても異常終了しない |
| FR-06 | 会社休業日を追加できる | `M/D` と `M/D-M/D` の形式を受け付け、不正入力はエラー表示して無視する |
| FR-07 | 連休候補を列挙する | 連続 3 日以上、かつ前後が出勤日である極大区間のみを候補とする |
| FR-08 | 効率順に並べる | 効率 = 連休日数 ÷ 使う有給日数。有給 0 日の連休は別枠で表示 |
| FR-09 | 年間プランを編成する | 有給残日数を超えず、候補が重複しない。選んだ優先モードの評価値が最大（同点時は有給消費が少ない方） |
| FR-09b | 優先モードを選べる | 「長い連休を優先」と「休みの回数を優先」を切り替えられ、結果が変わる |
| FR-10 | カレンダーを表示する | 対象期間の各月を表示し、祝日・休業日・有給候補・休日を色と記号で区別する |
| FR-11 | プランをコピーできる | クリップボードへプレーンテキストで出力。失敗時は選択可能なテキストを表示 |
| FR-12 | 設定を保存・削除できる | 再訪時に設定が復元される。「設定を消す」で即削除できる |
| FR-13 | 有給を取れない期間を指定できる | 繁忙期の出勤日は有給に使わず、その日をまたぐ連休も候補にしない |
| FR-14 | 有給を内訳で指定できる | 繰越分・今年度分を日数と失効日で入力でき、合計が予算になる |
| FR-15 | 付与日から失効日を導ける | 付与日を入れると、今年度分＝付与日の2年後の前日、繰越分＝その1年前が入る |
| FR-16 | 失効する日数を警告する | プランで使い切れずに失効する日数と、手持ちからまかなえない日数を日本語で示す |
| FR-17 | 失効日までの期間で計算できる | 対象期間に「失効日まで」を選べ、いちばん早い失効日が期間の終わりになる |
| FR-18 | カレンダーに取り込める | プランを iCalendar（.ics）で書き出す。連休と有給の日が終日予定になる |

## 6. 非機能要件

| ID | 分類 | 要件 |
|---|---|---|
| NFR-01 | 可搬性 | `index.html` をブラウザで開くだけで動作（ビルド・サーバー不要、`file://` でも可） |
| NFR-02 | 通信 | 外部への通信を一切行わない。Google Fonts も使わずシステムフォントで構成する |
| NFR-03 | 性能 | 12 か月ぶんの候補列挙と DP が、再計算 1 回あたり 50ms 未満（実測 1ms 程度） |
| NFR-04 | 対応環境 | モダンブラウザ（ES2020 モジュール、`Intl` 利用）。Node.js 20 以上でテスト実行 |
| NFR-05 | アクセシビリティ | コントラスト比 4.5:1 以上、色以外の手がかり併記、キーボードのみで全操作可能、`prefers-reduced-motion` 尊重 |
| NFR-06 | 日本語 | UI・メッセージ・エラーをすべて日本語で記述する |
| NFR-07 | 秘密情報 | 鍵・トークン・個人情報をコードに持たない。入力欄も設けない |

## 7. 用語

| 用語 | 定義 |
|---|---|
| 休日 | 勤務曜日ではない日、祝日、振替休日、国民の休日、会社休業日のいずれか |
| 出勤日 | 休日ではない日 |
| 連休 | 連続 3 日以上の休日の並び |
| 候補（ブリッジ） | 区間内のすべての出勤日に有給を当てると連休になる極大区間 |
| 効率 | 連休日数 ÷ その候補で使う有給日数 |
| プラン | 有給残日数の予算内で選んだ、重複しない候補の集合 |

## 8. 制約・免責

- 本アプリは非公式であり、休日の確定は官報（内閣府「国民の祝日について」）および各社の就業規則によること。
- 春分の日・秋分の日は、前年 2 月の官報で正式に確定する。本アプリの将来年の日付は近似式による計算値である。
- 有給の取得可否・申請手続きは勤務先の規程に従うこと。本アプリは申請機能を持たない。
- 対応年は 2016〜2099 年。範囲外の年を指定した場合はエラーメッセージを表示し、計算を行わない。
