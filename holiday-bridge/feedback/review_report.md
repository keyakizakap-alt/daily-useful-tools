## 1. 指摘一覧

深刻度: **高**＝誤った結果か使えない状態になる / **中**＝使い勝手または規約上の問題 / **低**＝改善提案

### R-01【高・実装中に判明】単純な日数最大化では「3 連休ばかり」になる

- **指摘者**: U3、A1
- **内容**: 当初のプランは「連休に含まれる日数の合計」を最大化していた。2026 年・有給 10 日で試算すると
  **3 連休が 13 件**並び、最長が 5 日にとどまった。有給 1 日を土日の隣に置くと +3 日になる一方、
  5 連休を 9 連休に伸ばしても +4 日にしかならないため、短い連休を量産する方が常に有利になる。
- **根拠**: 線形＝18 件 / 合計 61 日 / 最長 5 日、二乗＝8 件 / 合計 43 日 / 最長 13 日。
- **U3 の評価**: 「長い休みが欲しいのに、3 連休のリストを渡されても意味がない」
- **U2 の評価**: 「でも合計日数が多い方が得なケースもある。選ばせてほしい」

### R-02【高】会社休業日に「1/3」と書くと、黙って無視される

- **指摘者**: U2
- **内容**: 対象期間が「今日から 12 か月」（2026-10-12〜2027-10-11）のとき、年末年始の休業日として
  `1/3` と入力すると **2026-01-03**（過去）として解釈され、期間外のため計算に反映されない。
  エラーも警告も出ないため、利用者は「反映された」と誤認する。
- **再現**: `parseCompanyOff('1/3', 2026).dates === ['2026-01-03']` → 期間 2026-10-12〜2027-10-11 に含まれず、
  `buildCalendar` の会社休業日は 0 件。
- **影響**: 年末年始やゴールデンウィークを指定した利用者が、誤ったプランを正しいものとして受け取る。

### R-03【中】「保存した設定を消す」の結果が見えないことがある

- **指摘者**: U1、D1
- **内容**: 削除の完了メッセージを `#copy-status`（年間プランタブの中）に出しているため、
  **効率ランキングやカレンダーのタブを開いている間は押しても何も起きない**ように見える。
- **影響**: プライバシー上もっとも大事な操作のフィードバックが届かない（S2 からも同じ指摘）。

### R-04【中】セグメント切り替えが ARIA の radiogroup として不完全

- **指摘者**: D2
- **内容**: 「対象期間」「プランの優先の仕方」を `role="radiogroup"` / `role="radio"` で実装しているが、
  **矢印キーでの移動を実装していない**。ARIA の radiogroup はスクリーンリーダー利用者に
  矢印キーでの選択を期待させるため、宣言と挙動が食い違う。
- **影響**: 支援技術の利用者が操作方法を見つけられない。

### R-05【中】年の入力範囲が HTML と JavaScript に二重で書かれている

- **指摘者**: A2
- **内容**: `index.html` の `min="2016" max="2099"` と `holidays.js` の `SUPPORTED_YEARS` が別々に定義されている。
  対応年を変えたときに片方だけ直すと、入力欄だけ通って計算が落ちる、あるいはその逆が起きる。
- **影響**: 将来の保守で不整合が生まれる。現時点の動作に誤りはない。

### R-06【低】数値入力が確定（フォーカスを外す／Enter）まで反映されない

- **指摘者**: U1
- **内容**: 有給日数を `change` イベントで拾っているため、入力直後に「プランをコピー」を押すと
  **変更前のプランがコピーされる**ことがある。
- **影響**: 操作の因果が分かりにくい。計算は 1ms 程度なので、入力ごとの再計算で支障はない。

### R-07【低】全曜日を休みに設定したときの案内がない

- **指摘者**: U1、D1
- **内容**: 勤務曜日をすべて休みにすると、対象期間の全体が 1 つの連休（365 連休）として表示される。
  計算としては正しいが、設定ミスであることが多く、気づける手がかりがない。
  また `renderPlan` にある全曜日休み向けのメッセージは、候補が必ず 1 件できるため **到達しない分岐**になっている。

### R-09【高】`hidden` 属性が CSS に打ち消され、隠すべき要素が常に見えていた

- **指摘者**: D1、U1（画面の目視確認で発見）
- **内容**: `.inline-field { display: flex }`（年の入力欄）と `.fallback { display: block }`（コピーの代替テキスト）が
  **HTML の `hidden` 属性より強く効いてしまい**、「今日から12か月」を選んでいるのに年の入力欄が出たままになり、
  コピーを押していないのに「コピーできなかったため、以下を手動で選択してください。」が最初から表示されていた。
- **検出経緯**: 単体テストもスモークテストも通過していた（スモークは `isVisible()` を分岐条件にしか使っておらず、
  「隠れているべき」ことを検証していなかった）。**スクリーンショットの目視**で初めて判明した。
- **影響**: 初見の利用者に、関係のない入力欄とエラーメッセージを見せてしまう。

### R-10【中】年をまたぐ期間で、連休の日付に年が付かない

- **指摘者**: U2
- **内容**: 既定の対象期間「今日から12か月」は年をまたぐ（例: 2026-10-12〜2027-10-11）。
  この状態でプランを見ると「1月1日(金)〜1月3日(日)」と表示され、**2026 年なのか 2027 年なのか分からない**。
  コピーしたテキストを有給申請のメモに貼る場合、年が抜けていると実務上使えない。

### R-08【低】カレンダーの `role="list"` が 7 列グリッドの意味を伝えない

- **指摘者**: D2
- **内容**: 月カレンダーを `role="list"` + `role="listitem"` で表現している。曜日見出しと空白セルは
  `aria-hidden="true"` にしてあるため読み上げは壊れないが、「何曜日の列か」は各セルの
  `aria-label`（例: 「3月20日 金曜 春分の日」）に依存している。
- **判断**: `aria-label` に曜日と祝日名を含めているため情報は欠けていない。MVP では現状維持とする。

## 6. 今回の学び（次回に持ち越す）

1. **自動テストが通ることは「正しく見えている」ことを保証しない。**
   R-09 は 77 件の単体テストと 36 件のブラウザテストをすべて通過した状態で起きていた。
   `hidden` 属性のように CSS と HTML の優先順位が絡む不具合は、**スクリーンショットの目視**でしか見つからなかった。
   以後、UI を伴う変更では「隠れているべきものが隠れている」ことを明示的に検証する。

2. **「最適化」は目的関数を決めるまで終わらない。**
   R-01 は実装もテストも正しく、「連休に含まれる日数の合計を最大化する」という目的を正確に解いていた。
   それでも利用者の意図とは違った。アルゴリズムの正しさと、要件の正しさは別に検証する必要がある。

3. **入力の「黙った取りこぼし」は、エラーより危険。**
   R-02 は、エラーも警告も出さずに休業日を捨てていた。利用者は誤りに気づけない。
   解析器は「読めなかった」だけでなく「読めたが使わなかった」も報告する責任がある。

## 7. 追加した機能と、その理由

| # | 機能 | なぜ必要だったか |
|---|---|---|
| A | 有給を取れない期間（繁忙期） | 決算期などに有給は取れない。MVP は全出勤日を自由に使える前提で、提案がそのままでは使えなかった |
| B | 有給の内訳（繰越分・今年度分）と失効日 | 「有給10日」では、**どれがいつ失効するか**が表現できない。失効は実損なのに、MVP では扱えていなかった |
| C | 失効・不足の警告 | 下の R-11 を参照。黙って失効させるのが最悪の結果になる |
| D | 対象期間「失効日まで」 | C の警告に対する**実際に効く対処法**を 1 クリックで提供するため |
| E | iCalendar（.ics）書き出し | コピーしたテキストはカレンダーに入らない。申請とカレンダー登録が実際の最後の一歩 |

## 8. 第 2 ラウンドで見つかった不具合

### R-11【高】予算は足りているのに、プランが実行不能になる

- **検出**: 実装後、繰越分 10 日（2026-11-30 失効）＋今年度分 10 日の条件で手で動かして発見。
- **内容**: 「長い連休を優先」は有給を GW と秋に集めるため、11/30 までに有給を **1 日も置かない**。
  結果、合計 20 日の予算に対して実際に手持ちから出せるのは 10 日だけで、
  **プランがそのままでは実行できない**状態になっていた。
- **影響**: 利用者は 20 日ぶんの申請予定を受け取るが、10 日ぶんは有給が存在しない。
  しかも繰越分 10 日は黙って失効する。
- **対応**: 失効する日数と「手持ちからまかなえない日数」の両方を警告に出し、
  対処法（対象期間を「失効日まで」にする）を文面に含めた。
  対処法が実際に効くことを実測で確認している（失効 10 日 → 0 日）。

### R-12【中】日付入力の表示順がブラウザの言語設定で変わる

- **検出**: スクリーンショットの目視。
- **内容**: `<input type="date">` は Chromium ではブラウザの UI 言語に従って表示され、
  `11/30/2026` のように月日が逆に見える環境がある。失効日を 1 か月取り違えると実損につながる。
- **対応**: 解釈した日付を `= 2026年11月30日(月)` と日本語で併記した。

### R-13【高】対象期間のラベルに年が入っていなかった（R-10 の取りこぼし）

- **検出**: スクリーンショットの目視。
- **内容**: 第 1 ラウンドの R-10 で「年をまたぐ期間では連休カードに年を付ける」と対応したが、
  **対象期間のラベル自体**（`10月12日(月)〜10月11日(月)`）と、
  新設した失効日の表示を直していなかった。同じ種類の誤りを別の場所で再発させた。
- **対応**: 期間ラベルと失効日は、期間に関係なく常に年つきで表示するようにした。
  スモークに「対象期間の表示に年が入っている」を追加。

### R-14【中】サマリーの「有給の持ち数」が内訳を無視していた

- **検出**: ブラウザでの手動確認。
- **内容**: 内訳で合計 20 日を指定しても、サマリーには単純入力の `10日` が出ていた。
  `state.leaveDays` を直接読んでいたため。
- **対応**: 実際の予算を返す `leaveBudget()` に統一した。

## 11. 今回の学び（第 1 ラウンドの学びの続き）

4. **「正しいプラン」と「実行できるプラン」は違う。**
   R-11 は最適化としては正解を出していた。予算 20 日を使い切る解を見つけている。
   足りなかったのは「その有給は**その時点で手元にあるのか**」という時間軸の検証だった。
   制約を予算という 1 つの数字に潰した時点で、この種の誤りは構造的に入り込む。

5. **同じ誤りは別の場所で再発する。**
   R-13 は R-10 とまったく同じ「年を省略した」誤りを、別の表示箇所でやっていた。
   1 件を直したときに「同じ種類の箇所が他にないか」を探していれば防げた。
